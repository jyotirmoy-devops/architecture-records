# 1. Executive Summary

This document defines a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US. The solution is designed for 10,000 requests per minute, autoscaling, 99.99% uptime objective in a single region, and PCI-DSS-aligned encryption controls.

The architecture is private-by-default:
- AKS runs as a private cluster with no public IPs on nodes
- Application Gateway WAF v2 is the only internet-facing entry point
- Azure Container Registry (ACR), Azure Key Vault, Azure Cache for Redis Premium, and Azure Database for MySQL Flexible Server all have public network access disabled
- All PaaS services are reachable exclusively through Private Endpoints
- Private DNS zones are used for name resolution
- Monitoring and diagnostics are centralized

# 2. Business and Technical Requirements

## 2.1 Business Requirements
- Customer-facing web application
- 10,000 requests per minute
- Autoscaling required
- 99.99% uptime target in East US
- PCI-DSS encryption standards apply

## 2.2 Technical Constraints
- AKS nodes must not have public IPs
- Ingress must be via Application Gateway WAF v2
- Azure Cache for Redis Premium required
- Azure Database for MySQL Flexible Server required
- All PaaS services must have public network access entirely disabled
- All PaaS services must be connected exclusively via Private Endpoints

# 3. Target Architecture Overview

## 3.1 Core Components
- Azure Application Gateway WAF v2
- Azure Kubernetes Service (private cluster)
- Azure Container Registry Premium
- Azure Key Vault
- Azure Cache for Redis Premium
- Azure Database for MySQL Flexible Server
- Azure Monitor / Log Analytics
- Private DNS Zones

## 3.2 Logical Flow
1. Customer connects over HTTPS to Application Gateway WAF v2
2. WAF inspects and forwards traffic to AKS ingress
3. AKS web and API pods process the request
4. Application services use Redis for caching/session acceleration
5. Application services use MySQL for transactional persistence
6. Secrets and certificates are retrieved from Key Vault
7. Container images are pulled from ACR during deployment
8. Logs and diagnostics are sent to Azure Monitor / Log Analytics

# 4. Application and Solution Design

## 4.1 Recommended Pattern
Use a Web-API-Data pattern with stateless services and cache-aside behavior.

### Core patterns
- Stateless web/API services on AKS
- Cache-aside pattern with Redis
- Idempotent command handling for writes
- Circuit breaker and retry with backoff for downstream calls
- Health probe-driven autoscaling
- Blue/green or canary deployment for releases

### Not recommended
- Event sourcing for the core transactional system unless explicitly required
- Chatty synchronous microservice communication
- Stateful workloads in AKS unless unavoidable

## 4.2 Suggested Service Boundaries
1. Web Frontend Service
   - Serves UI and static content
   - Calls backend APIs only
   - No direct database access

2. Customer API Service
   - Handles customer-facing business operations
   - Owns validation, orchestration, and authorization checks
   - Reads/writes MySQL
   - Uses Redis for caching and short-lived state

3. Identity/Session Adapter
   - Integrates with external identity provider if needed
   - Manages session/token validation
   - Prefer stateless JWT validation over server-side sessions

4. Admin/Backoffice API if required
   - Separate from customer-facing APIs
   - Stronger authorization boundaries
   - Isolated by namespace and network policy

# 5. Network and Connectivity Design

## 5.1 Ingress
- Internet -> Application Gateway WAF v2 -> AKS ingress
- HTTPS only
- TLS 1.2+ enforced
- Prefer end-to-end encryption where practical

## 5.2 East-West Traffic
- Service-to-service communication inside AKS
- Prefer REST/HTTPS for simplicity and observability
- Use gRPC only where latency and throughput justify it
- Enforce Kubernetes Network Policies
- Use namespace isolation for environment or domain separation

## 5.3 Private Endpoint Connectivity
All PaaS services are private-only:
- ACR via Private Endpoint
- Key Vault via Private Endpoint
- Redis via Private Endpoint
- MySQL via Private Endpoint

## 5.4 Private DNS Zones
Private DNS zones linked to the AKS VNet:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

# 6. Security Architecture

## 6.1 Identity and Access
- Microsoft Entra ID as the identity provider
- Managed identities for AKS workloads and platform integrations
- MFA for privileged access
- PIM for just-in-time elevation
- No shared admin accounts
- No long-lived secrets in code or CI/CD variables

## 6.2 Network Security
- AKS nodes in private subnets
- No public IPs on nodes
- Application Gateway WAF v2 is the only public entry point
- Public access disabled on all PaaS services
- NSGs on all subnets
- Deny-by-default egress posture
- WAF in front of all customer traffic

## 6.3 Encryption
- TLS 1.2+ in transit
- Encryption at rest for all services
- Key Vault for secrets and keys
- Prefer customer-managed keys where supported and justified
- Key rotation policy required

## 6.4 PCI-DSS Controls
- Minimize cardholder data storage
- Prefer tokenization or external payment processing
- Avoid logging PAN, CVV, secrets, or tokens
- Restrict access to logs and secrets on a need-to-know basis
- Enable audit logging for sensitive operations

# 7. Data Architecture

## 7.1 Azure Database for MySQL Flexible Server
- Primary system of record
- Private access only
- Public network access disabled
- Zone-redundant HA where supported
- Automated backups enabled
- Point-in-time restore enabled
- TLS enforced
- Least-privilege database users

## 7.2 Azure Cache for Redis Premium
- Private Endpoint only
- Public network access disabled
- Use for caching, session acceleration, and rate limiting
- Do not store long-term system-of-record data

## 7.3 Azure Key Vault
- Private Endpoint only
- Public network access disabled
- Store secrets, certificates, and keys
- Soft delete and purge protection enabled
- Diagnostic logging enabled

## 7.4 Azure Container Registry
- Premium SKU
- Private Endpoint only
- Public network access disabled
- Access only from AKS via managed identity

# 8. Availability and Resilience

## 8.1 High Availability Pattern
To support the 99.99% target in a single region:
- Deploy AKS across multiple availability zones
- Use zone-redundant Application Gateway WAF v2 where available
- Use zone-redundant MySQL Flexible Server HA where supported
- Use Redis Premium HA where applicable
- Use Pod Disruption Budgets and topology spread constraints

## 8.2 Resilience Controls
- Pod autoscaling
- Node autoscaling
- Health probes on ingress and services
- Backup and restore procedures
- Failure testing for pod eviction, node loss, zone loss, WAF misconfiguration, private endpoint DNS failure, and database failover

# 9. Observability and Audit

## 9.1 Required Telemetry
- Request latency
- Error rate
- Saturation
- Pod restarts
- Redis hit ratio
- MySQL connection pool health
- WAF blocks
- Authentication failures
- Secret access events

## 9.2 Logging Guidance
- Do not log cardholder data, secrets, tokens, or full PII
- Correlate requests with trace IDs
- Centralize audit logs for security review
- Restrict access to logs

# 10. Deployment and Release Strategy

- Build container image
- Scan image for vulnerabilities
- Push to ACR via private connectivity
- Deploy to AKS using progressive rollout
- Validate health and metrics
- Promote or rollback automatically
- Use signed images and digest pinning where available

# 11. Risks and Mitigations

## 11.1 Private DNS Misconfiguration
Mitigation: Standardize private DNS zones and validate name resolution in deployment pipelines.

## 11.2 MySQL Bottleneck
Mitigation: Use Redis caching, query optimization, read reduction, and connection pooling.

## 11.3 WAF False Positives
Mitigation: Start in detection mode during testing, then tune rules before enforcement.

## 11.4 Overly Chatty Microservices
Mitigation: Keep service count low and prefer coarse-grained APIs.

## 11.5 PCI Scope Expansion
Mitigation: Minimize storage of sensitive data and isolate payment-related flows.

# 12. Final Recommended Application Flow
1. Customer sends HTTPS request to Application Gateway WAF v2
2. WAF forwards to AKS ingress
3. Web/API service authenticates and validates request
4. Service checks Redis for cached data
5. If cache miss, service queries MySQL
6. Sensitive configuration and secrets are retrieved from Key Vault
7. Any background work is sent to a queue and processed by a worker
8. Response is returned to the customer
9. Logs, metrics, and audit events are emitted for monitoring and compliance

# 14. Conclusion

This architecture is appropriate for a secure, PCI-aligned, customer-facing application in East US with high availability and private-only PaaS connectivity. The most important implementation details are:
- enforce private DNS correctly,
- prevent any public network fallback,
- use managed identities end-to-end,
- validate MySQL HA and backup restore procedures,
- and test autoscaling under realistic load before production cutover.
