# 1. Overview

This document defines the technical architecture for a simple internal HR web portal used to track employee leave requests and status updates.

The original requirement asked for a standard website with login and a backend database. The expert reports refine that request into an enterprise-controlled internal business application because the solution handles sensitive HR and employee data. As a result, the architecture below uses corporate identity, private networking, centralized logging, encryption, and role-based access control.

## Why the original requirement was altered

The original request was intentionally simple, but the expert reports identify that HR records are sensitive and must be treated as regulated business data. Therefore, the design is expanded to include:
- Microsoft Entra ID single sign-on
- MFA and conditional access for privileged roles
- private database connectivity
- centralized audit logging
- encryption in transit and at rest
- managed secrets
- role-based authorization

These changes are required to meet enterprise security and compliance expectations.

# 2. Architecture Summary

## Recommended solution pattern
- Modular monolith
- Layered web application
- REST API over HTTPS
- Relational database as system of record
- Optional queue-based async processing later for notifications and reporting

## Core components
- Azure App Service Standard S1 for the web portal
- Azure SQL Database General Purpose, Serverless for transactional data
- Azure Key Vault Standard for secrets and certificates
- Application Insights and Azure Monitor for observability
- Azure Cache for Redis for session state and caching
- Azure Blob Storage for attachments and exports
- Microsoft Entra ID for authentication
- Dedicated VNet with private endpoints and VNet integration

# 3. Logical Architecture

## User access flow
1. HR user or manager opens the web portal.
2. Authentication is performed through Microsoft Entra ID.
3. The portal calls the backend API over HTTPS.
4. The backend applies RBAC and business rules.
5. The backend reads and writes data in Azure SQL Database.
6. Secrets are retrieved from Azure Key Vault using managed identity.
7. Logs and metrics are sent to Application Insights and Azure Monitor.

## Application responsibilities
- Web UI for login and request management
- Backend API for business logic
- Workflow state management for leave requests
- Audit trail for all sensitive changes
- Optional caching for performance
- Optional document storage for attachments

# 4. Physical Azure Architecture

## Web tier
- Azure App Service Plan: Standard S1
- Azure App Service Web App: Standard S1
- Built-in authentication with Microsoft Entra ID
- HTTPS only
- Anonymous access disabled

## Data tier
- Azure SQL Server logical server
- Azure SQL Database: General Purpose, Serverless
- Suggested baseline: 1 vCore min / 2 vCore max
- Automated backups enabled
- Point-in-time restore enabled

## Secrets and configuration
- Azure Key Vault Standard
- Store connection strings, certificates, and application secrets
- Access via managed identity only

## Observability
- Application Insights
- Log Analytics Workspace
- Azure Monitor alerts for:
  - app availability
  - HTTP 5xx rate
  - SQL utilization
  - failed sign-ins
  - Key Vault access failures

# 5. Network Architecture

## Virtual network
- VNet: `vnet-hr-portal-prod`
- Address space: `10.40.0.0/16`

## Subnets
1. `snet-appsvc-integration`
   - CIDR: `10.40.1.0/24`
   - Delegated to `Microsoft.Web/serverFarms`

2. `snet-private-endpoints`
   - CIDR: `10.40.2.0/24`
   - Private endpoint network policies disabled

3. Optional future subnet
   - `snet-management`
   - Reserved for admin tooling or jump access if ever needed

## Private DNS zones
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`
- Optional future zones:
  - `privatelink.blob.core.windows.net`
  - `privatelink.file.core.windows.net`

## Network controls
- Database must not be publicly reachable
- Key Vault must not be publicly reachable
- Private endpoints used for SQL and Key Vault
- App Service uses regional VNet integration
- Inbound access to the portal should be limited to approved corporate access paths where possible
- Outbound traffic should be restricted to required services only

# 6. Security Architecture

## Identity and access management
- Microsoft Entra ID only for user authentication
- No local user accounts for normal users
- MFA required for all HR users and administrators
- Conditional Access required for privileged roles
- No shared admin accounts
- Least privilege enforced for users and service identities

## RBAC roles
- HR User
- HR Approver / Manager
- HR Admin
- System Administrator

## Application authorization
- Role-based authorization enforced in the application
- Separate permissions for:
  - request submission
  - approval
  - rejection
  - administration
  - reporting

## Secrets management
- No secrets in source code
- No secrets in plain-text config files
- No secrets in CI/CD variables in plain text
- Use managed identity to access Key Vault

## Encryption
- TLS 1.2+ for all traffic
- HTTPS required
- Encryption at rest for all stored employee data and backups
- Customer-managed keys may be used if required by policy

# 7. Data Architecture

## System of record
- Azure SQL Database

## Supporting data services
- Azure Cache for Redis for transient session state and caching
- Azure Blob Storage for attachments, exports, and archival documents

## Core data entities
- Employees
- LeaveRequests
- LeaveApprovals
- LeaveBalances
- LeaveTypes
- AuditLog

## Data handling principles
- Keep employee master data in SQL, not Redis
- Keep approvals and workflow state in SQL
- Store attachments separately in Blob Storage
- Do not log sensitive employee content in application logs
- Maintain immutable audit history for sensitive changes

# 8. Application Design

## Recommended pattern
- Modular monolith with internal modules for:
  - authentication and authorization
  - employee management
  - leave request management
  - workflow state management
  - audit/history logging
  - reporting/query views

## API style
- REST over HTTPS

## Workflow states
- Draft
- Submitted
- Approved
- Rejected
- Cancelled

## Future extensibility
If the system grows, the first candidates for extraction are:
- notifications service
- reporting service

# 9. Availability, Backup, and Recovery

## Availability
- App Service platform HA is sufficient for the initial design
- SQL serverless provides automated platform-managed resilience

## Backup strategy
- SQL automated backups enabled by default
- Point-in-time restore for accidental deletes or bad updates
- Geo-restore for regional recovery
- Long-term retention if required by HR or legal policy
- Blob Storage soft delete and versioning if attachments are important

## RTO / RPO targets
Recommended baseline:
- RTO: 1–4 hours
- RPO: 15 minutes to 1 hour

# 10. Governance and Compliance

## Governance requirements
- Data classification review before build
- Privacy impact assessment
- Threat modeling before implementation
- Define data ownership:
  - HR owns the business process
  - IT owns platform operations
  - Security owns control validation

## Logging requirements
Log all of the following:
- sign-ins and failed sign-ins
- record creation, update, approval, rejection, deletion
- permission changes
- admin configuration changes
- database access events where supported

Logging requirements:
- centralized
- tamper-resistant
- retained per corporate policy
- searchable for audit and incident response
- correlation IDs included across web and database actions

## Compliance posture
This is a standard internal business application with sensitive data classification. It should follow enterprise baseline controls aligned to least privilege, strong identity, auditability, encryption, and network isolation.

# 11. Deployment Pattern

Recommended deployment order:
1. Deploy VNet and subnets
2. Deploy Key Vault and SQL private endpoints
3. Deploy SQL Database
4. Deploy App Service Plan and Web App
5. Enable Entra ID authentication
6. Configure managed identity and SQL permissions
7. Configure VNet integration
8. Add monitoring and alerts

# 13. Final Recommendation

Proceed with the secure internal HR portal design using:
- Azure App Service Standard S1
- Azure SQL Database General Purpose, Serverless
- Azure Key Vault Standard
- Azure Cache for Redis
- Azure Blob Storage
- Microsoft Entra ID authentication
- Private endpoints and VNet integration
