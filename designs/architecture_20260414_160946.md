## 1. Executive Summary

Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US, built for 10,000 requests per minute, with auto-scaling, 99.99% uptime target, PCI-DSS-aligned encryption, and no public exposure for AKS nodes or PaaS dependencies.

The application will use:
- AKS for containerized application workloads
- Application Gateway WAF v2 as the only internet ingress
- Azure Cache for Redis (Premium) for low-latency caching/session acceleration
- Azure Database for MySQL Flexible Server for transactional persistence
- Azure Container Registry (ACR) for images
- Azure Key Vault for secrets, certificates, and encryption material
- Private Endpoints only for all PaaS services
- Private DNS zones to resolve all private service names internally

## 2. Requirements Summary

### Business / Availability
- Customer-facing web application
- 10,000 requests per minute
- Auto-scaling required
- 99.99% uptime target
- Single region: East US

### Security / Compliance
- PCI-DSS encryption standards apply
- AKS nodes must not have public IPs
- Ingress only through Application Gateway WAF v2
- All PaaS services must have public network access disabled and be reachable only through Private Endpoints

### Services in Scope
- AKS
- Application Gateway WAF v2
- Azure Container Registry (ACR)
- Azure Key Vault
- Azure Cache for Redis Premium
- Azure Database for MySQL Flexible Server

## 3. Architecture Overview

### Recommended application pattern
A secure, stateless, customer-facing AKS application using a small set of bounded-context services, fronted by Application Gateway WAF v2, with REST for synchronous access, queue/event-driven workers for asynchronous processing, Redis for caching, MySQL for transactional state, and Private Endpoints for every PaaS dependency.

### Core design principles
- Zero public PaaS exposure
- Private-by-default networking
- Least privilege identity access
- Encryption everywhere
- Stateless application tier; state externalized to managed services
- Multi-zone resilience within East US

## 4. Logical Architecture

### Edge / Ingress
- Azure Application Gateway WAF v2
  - Public frontend IP for customer ingress
  - WAF in Prevention mode
  - TLS termination at gateway
  - Optional end-to-end TLS to AKS ingress

### Container Platform
- Azure Kubernetes Service (AKS)
  - Private cluster recommended
  - System and user node pools in Availability Zones
  - Cluster autoscaler enabled
  - No public IPs on nodes
  - Azure CNI Overlay or Azure CNI depending IP planning

### Container Registry
- Azure Container Registry Premium
  - Public network access disabled
  - Private Endpoint enabled
  - Private DNS integration

### Secrets / Certificates
- Azure Key Vault
  - Public network access disabled
  - Private Endpoint enabled
  - Use for TLS certs, app secrets, and encryption keys

### Cache
- Azure Cache for Redis Premium
  - Public network access disabled
  - Private Endpoint enabled
  - Use for session/state caching

### Database
- Azure Database for MySQL Flexible Server
  - Private access only
  - Public network access disabled
  - Private Endpoint enabled
  - Zone-redundant deployment if available/required for HA posture

### Observability
- Log Analytics Workspace
- Azure Monitor / Container Insights
- Application Gateway diagnostics to Log Analytics
- Key Vault diagnostics
- MySQL and Redis diagnostics where supported

## 5. Target Network Topology

### Virtual Network
Create a dedicated VNet in East US with segmented subnets.

**Suggested VNet address space**
- `10.20.0.0/16`

**Subnets**
1. **AppGatewaySubnet**
   - `10.20.0.0/24`
   - Dedicated only to Application Gateway WAF v2

2. **AKS-NodeSubnet**
   - `10.20.1.0/22`
   - AKS node pools
   - No public IPs
   - NSG restricted to required east-west and ingress flows

3. **PrivateEndpointSubnet**
   - `10.20.8.0/24`
   - Private Endpoints for:
     - ACR
     - Key Vault
     - Redis
     - MySQL
   - Disable private endpoint network policies on this subnet

4. **AzureBastionSubnet** or **ManagementSubnet** if operational access is needed
   - Prefer Azure Bastion for admin access
   - Avoid jumpbox public exposure

### Private DNS Zones
Create and link these Private DNS Zones to the VNet:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

If AKS is deployed as a private cluster, also include the region-specific AKS private DNS zone used by the cluster.

## 6. Security Architecture

### Internet Exposure
- Only Application Gateway WAF v2 has a public IP
- AKS nodes have no public IPs
- All PaaS services are private-only

### Private Endpoint Enforcement
For each PaaS service:
- Disable public network access
- Create Private Endpoint
- Configure Private DNS Zone
- Restrict access via VNet and NSGs

### AKS Security Controls
- Private AKS cluster
- Azure AD integration / Entra ID
- Kubernetes RBAC
- Azure Policy for AKS
- Pod Security Admission or equivalent hardened policy
- Network Policies enabled
- Managed identities for workload access to ACR, Key Vault, and other services
- Use Secrets Store CSI Driver with Key Vault provider

### WAF Controls
- WAF policy in Prevention mode
- OWASP managed rules
- Custom rules for geo/IP restrictions, rate limiting, bot mitigation, header validation, and path restrictions

### PCI-DSS Encryption
- TLS 1.2+ externally and internally
- Encryption at rest for all data services
- Customer-managed keys (CMK) where supported and required by policy
- Key Vault for certificate and key lifecycle management

## 7. Availability and Resiliency Design

### Availability Target
A 99.99% single-region target is aggressive. To maximize resilience in East US:
- Deploy Application Gateway WAF v2 with zone redundancy
- Deploy AKS node pools across multiple availability zones
- Use AKS Uptime SLA
- Use multiple replicas for all stateless services
- Use PodDisruptionBudgets
- Use readiness/liveness probes
- Use cluster autoscaler and HPA

### Important Note
Microsoft guidance indicates that for 99.99%+ targets, multi-region is generally recommended for mission-critical workloads. Since the requirement is explicitly single-region, the design should be treated as best-effort 99.99% within East US, with the understanding that true end-to-end SLA depends on the exact service SKUs and configuration.

## 8. Application and Data Flow

### Request flow
1. Customer connects to Application Gateway WAF v2
2. WAF inspects and forwards HTTPS traffic
3. Application Gateway routes to AKS ingress
4. AKS ingress routes to application services
5. Application services access:
   - Redis via Private Endpoint
   - MySQL via Private Endpoint
   - Key Vault via Private Endpoint
   - ACR via Private Endpoint for image pulls

### Data strategy
- Keep application pods stateless
- Store session state in Redis Premium
- Persist durable business state in MySQL Flexible Server
- Do not store secrets in container images, environment variables, or ConfigMaps
- Use Key Vault CSI Driver or workload identity-based secret retrieval

## 9. Identity and Access

### Identity model
- Use Microsoft Entra ID for human access
- Use AKS Workload Identity for pod-to-Azure service authentication
- Avoid shared credentials
- Use managed identities wherever supported
- Apply least privilege RBAC to AKS, Key Vault, ACR, MySQL, and Redis

### Access model
- No shared credentials in containers
- No secrets in images or manifests
- Least privilege RBAC
- Separate identities per namespace or application tier if needed

## 10. Security and Compliance Controls

### PCI-DSS alignment
Key controls:
- Minimize cardholder data scope
- Segment PCI-sensitive service boundaries
- Encrypt data in transit and at rest
- Centralize secrets in Key Vault
- Strong audit logging
- Least privilege access
- Regular image scanning and dependency scanning
- No secrets in environment variables unless injected securely and rotated
- No public exposure of PaaS services

### Network security
- AKS nodes: no public IPs
- Ingress: Application Gateway WAF v2 only
- All PaaS services: public network access disabled
- All PaaS services: Private Endpoints only
- Private DNS zones required for Key Vault, ACR, Redis, and MySQL
- AKS pods resolve PaaS endpoints privately

### Container security
- Images built in CI/CD and pushed to ACR
- Image scanning before deployment
- Signed images preferred
- Run containers as non-root
- Read-only root filesystem where possible
- Drop Linux capabilities not needed
- Use pod security controls and network policies
