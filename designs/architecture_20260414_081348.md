# Technical Architecture Document (TAD)

## 1. Executive Summary

Design a highly secure, customer-facing web application on **Azure Kubernetes Service (AKS)** in **East US** with:
- **10,000 requests per minute** expected load
- **Auto-scaling** for both pods and nodes
- **99.99% uptime target** in a single region
- **PCI-DSS-aligned encryption and secret handling**
- **No public IPs on AKS nodes**
- **Ingress only through Application Gateway WAF v2**
- **All PaaS dependencies reachable only through Private Endpoints**
- Data/state services:
  - **Azure Cache for Redis (Premium)**
  - **Azure Database for MySQL Flexible Server**
  - **Azure Container Registry**
  - **Azure Key Vault**

This document combines the target architecture, security controls, governance requirements, and cost baseline.

## 2. Architecture Objectives

- Provide a secure public web entry point through Application Gateway WAF v2.
- Keep AKS nodes private with no public IPs.
- Enforce private-only access for ACR, Key Vault, Redis, and MySQL.
- Support 10,000 requests/minute with horizontal and cluster autoscaling.
- Align with PCI-DSS encryption, logging, and least-privilege requirements.
- Maintain a single-region East US deployment with zone-aware resilience where supported.

## 3. Target Solution Overview

### 3.1 Application Pattern
Use a **modular microservices architecture** with a **Web-API + async worker** pattern:
- Web tier: stateless API services running in AKS
- Async processing tier: background workers for non-blocking tasks
- CQRS-lite where useful
- Event-driven integration for internal decoupling
- Transactional Outbox pattern for reliable event publication

### 3.2 Core Azure Services
- **Azure Kubernetes Service (AKS)**
- **Application Gateway WAF v2**
- **Azure Cache for Redis Premium**
- **Azure Database for MySQL Flexible Server**
- **Azure Key Vault**
- **Azure Container Registry (ACR)**
- **Azure Private DNS Zones**
- **Azure Monitor / Log Analytics**
- **Microsoft Defender for Cloud**
- **Azure Policy**

## 4. Network and Connectivity Design

### 4.1 Ingress
- **Application Gateway WAF v2** is the only public ingress path.
- WAF must run in **Prevention mode** for production.
- Enforce HTTPS only and TLS 1.2+.
- Use AGIC or equivalent ingress integration to route traffic to AKS.

### 4.2 AKS
- AKS nodes must not have public IPs.
- Prefer a private cluster or equivalent private networking posture.
- Use managed identity for cluster operations.
- Enable Cluster Autoscaler and HPA.

### 4.3 Private Endpoint-Only PaaS Access
All of the following must have **public network access disabled** and be reachable **exclusively via Private Endpoints**:
- Azure Container Registry
- Azure Key Vault
- Azure Cache for Redis Premium
- Azure Database for MySQL Flexible Server

### 4.4 Private DNS
Required private DNS zones:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

These zones must be linked to the application VNet so AKS workloads resolve private IPs only.

## 5. Security Architecture

### 5.1 Identity and Access
- Use **Entra ID** for administrators.
- Enforce **MFA** for privileged users.
- Require **PIM** for just-in-time elevation.
- Use **Conditional Access** for admin access.
- Prefer **managed identities** and **Azure Workload Identity** for pods.
- Prohibit long-lived secrets in code, images, or CI logs.

### 5.2 Least Privilege
- Restrict Kubernetes RBAC to minimal required roles.
- Scope ACR, Key Vault, Redis, and MySQL access narrowly.
- Separate platform, security, application, and audit roles.

### 5.3 Encryption
- Enforce **TLS 1.2 minimum** everywhere.
- Encrypt data at rest for all services.
- Prefer **customer-managed keys (CMK)** where supported and operationally feasible.
- Use Key Vault for secrets, certificates, and keys.
- Rotate secrets and keys on a defined schedule.

### 5.4 Logging and Monitoring
Mandatory log sources:
- Application Gateway WAF logs
- AKS control plane logs
- AKS audit logs
- Container and application logs
- Key Vault diagnostic logs
- ACR audit/access logs
- Redis diagnostic logs
- MySQL audit/slow query/security logs where available
- Entra ID sign-in and audit logs
- Azure Activity Logs
- Network flow/security logs where applicable

Centralize logs in a SIEM/SOC platform and protect them from tampering.

## 6. Availability and Resilience

### 6.1 Availability Target
The design targets **99.99% uptime in East US**. This is a service objective, not a guarantee against regional outages.

### 6.2 Resilience Measures
- Zone-redundant Application Gateway WAF v2 where supported
- AKS node pools spread across Availability Zones 1, 2, and 3
- Multiple replicas for all application pods
- Pod anti-affinity and topology spread constraints
- Pod Disruption Budgets
- Cluster Autoscaler and HPA
- Redis Premium configured for high availability
- MySQL Flexible Server configured for HA where supported

### 6.3 Operational Resilience
- Stateless services
- Graceful shutdown and connection draining
- Timeouts, retries with jitter, and circuit breakers
- Idempotency keys for write APIs
- Blue/green or canary deployment strategy

## 7. Data Architecture

### 7.1 Azure Cache for Redis Premium
Use Redis for:
- Session state
- Response caching
- Distributed locks
- Rate limiting counters
- Short-lived tokens

Configuration:
- Premium tier
- Private Endpoint only
- Public network access disabled
- TLS enforced in transit
- Treat as ephemeral state; do not store system-of-record data

### 7.2 Azure Database for MySQL Flexible Server
Use MySQL as the system of record for transactional data.

Configuration:
- Private access only
- Public network access disabled
- TLS 1.2+ for all client connections
- Least-privilege DB accounts per service
- Automated backups and point-in-time restore

### 7.3 Azure Blob Storage
Use Blob Storage for:
- Backups
- Exports
- Audit artifacts
- Immutable retention where required

Configuration:
- Private Endpoint only
- Public network access disabled
- Lifecycle policies, soft delete, and versioning where appropriate

## 8. Application Communication Pattern

- External/public APIs: REST/JSON
- Internal service calls: REST/JSON by default
- gRPC only for high-throughput low-latency internal paths
- Async events/queues for notifications, audit fan-out, reconciliation, and long-running workflows
- Transactional Outbox pattern to prevent dual-write inconsistency

## 9. Governance and Compliance

### 9.1 PCI-DSS Alignment
- Encrypt data in transit using TLS 1.2+
- Encrypt data at rest
- Use Key Vault-backed secret management
- Enforce least privilege and network isolation
- Centralize audit logging and monitoring
- Minimize PCI scope by avoiding storage of PAN/CVV unless absolutely required

### 9.2 Policy Enforcement
Use Azure Policy to deny:
- Public network access on approved PaaS services
- Public IP assignment to AKS nodes
- Noncompliant TLS settings
- Missing diagnostic settings

Use policy-as-code in CI/CD for identity bindings, network rules, diagnostic settings, and private endpoint requirements.

## 10. Operational Controls

- Azure Monitor + Log Analytics for observability
- Alerts for WAF blocks, 5xx rates, autoscaling events, DNS failures, private endpoint failures, and database/cache health
- Documented runbooks for restore, failover, and incident response
- Infrastructure as Code required for repeatable rebuilds

## 11. Key Design Decisions

| Area | Decision |
|---|---|
| Application style | Modular microservices |
| Sync communication | REST/HTTPS, optional gRPC internally |
| Async communication | Queue/event-driven workers |
| Data access | MySQL for system of record, Redis for cache/session |
| Consistency | Transactional Outbox + idempotent consumers |
| Security | Private endpoints only, managed identity, Key Vault secrets |
| Ingress | Application Gateway WAF v2 only |
| Compliance | PCI-DSS-aligned encryption and least-privilege access |
| Availability | Stateless services, HPA, retries, circuit breakers |
