# Technical Architecture Document

## 1. Executive Summary
This document defines a secure, customer-facing web application architecture on Azure Kubernetes Service (AKS) in East US. The design supports 10,000 requests per minute with autoscaling, PCI-DSS-aligned encryption and access controls, and private-only connectivity for all PaaS dependencies.

The architecture uses:
- Azure Application Gateway WAF v2 as the only public ingress
- A private AKS cluster with no public IPs on nodes
- Azure Cache for Redis Premium and Azure Database for MySQL Flexible Server
- Azure Container Registry and Azure Key Vault with public network access disabled
- Private Endpoints and Private DNS Zones for all PaaS services
- Microsoft Entra ID, managed identities, and least-privilege RBAC
- Centralized logging and monitoring

### Important compliance and availability caveat
The original requirement requested 99.99% uptime in a single region. The expert reports indicate that, for this full stack, a guaranteed composite SLA of 99.99% is not realistically supportable in a single region. The design therefore follows the expert reports and targets the highest practical single-region resilience in East US, with zone-redundant components where supported. This is an intentional adjustment to the original requirement because the expert analysis identified a more realistic availability ceiling for the selected Azure services and topology.

## 2. Scope and Design Goals
- Customer-facing web application
- East US deployment
- 10,000 requests per minute
- Autoscaling at pod and node levels
- PCI-DSS-aligned encryption and auditability
- No public IPs on AKS nodes
- Ingress only through Application Gateway WAF v2
- All PaaS services reachable only through Private Endpoints
- Public network access disabled for ACR, Key Vault, Redis, and MySQL

## 3. Target Architecture Overview
### 3.1 Logical flow
1. Users connect over HTTPS to Application Gateway WAF v2.
2. WAF inspects and forwards traffic to AKS ingress.
3. AKS routes requests to stateless application services.
4. Application services use Redis and MySQL over private connectivity.
5. Images are pulled from private ACR.
6. Secrets and certificates are retrieved from private Key Vault.
7. Logs and metrics are sent to Azure Monitor and Log Analytics.

### 3.2 Application pattern
The application should follow a stateless Web/API pattern with optional queue-based workers for asynchronous tasks. A modular monolith or well-bounded microservices approach is acceptable depending on team maturity.

Recommended patterns:
- Web-API pattern for synchronous customer requests
- Web-Queue-Worker pattern for long-running or retryable tasks
- CQRS-lite where read/write separation improves scalability
- Event-driven integration for internal asynchronous workflows

Not recommended:
- Full event sourcing unless explicitly required
- Sticky sessions

## 4. Azure Services Selected
### 4.1 Public ingress / edge
- Azure Application Gateway WAF v2
  - Internet-facing
  - WAF in Prevention mode
  - Zone-redundant deployment where supported
  - Autoscaling enabled
  - Static VIP
  - TLS termination with certificate sourced from Key Vault

### 4.2 Compute
- Azure Kubernetes Service (AKS)
  - Private cluster
  - System and user node pools in Availability Zones
  - Cluster autoscaler enabled
  - Horizontal Pod Autoscaler enabled
  - No public IPs on nodes

### 4.3 Container supply chain
- Azure Container Registry Premium
  - Public network access disabled
  - Private Endpoint only

### 4.4 Secrets / certificates
- Azure Key Vault
  - Public network access disabled
  - Private Endpoint only
  - Soft delete and purge protection enabled
  - Used for TLS certs, secrets, and keys

### 4.5 Cache
- Azure Cache for Redis Premium
  - Public network access disabled
  - Private Endpoint only
  - Zone redundancy enabled where supported

### 4.6 Database
- Azure Database for MySQL Flexible Server
  - Public network access disabled
  - Private Endpoint only
  - Zone-redundant HA enabled where supported

### 4.7 Observability
- Azure Monitor
- Log Analytics Workspace
- Application Insights
- Optional SIEM integration

## 5. Network Topology
### 5.1 Virtual network
Recommended VNet: `vnet-eastus-custweb-01`

### 5.2 Subnets
- `snet-appgw` — dedicated subnet for Application Gateway WAF v2
- `snet-aks-system` — AKS system node pool
- `snet-aks-user` — AKS application node pool(s)
- `snet-private-endpoints` — Private Endpoints for ACR, Key Vault, Redis, MySQL
- `snet-azure-bastion` — optional secure admin access
- `snet-firewall` — optional if explicit egress inspection is required

### 5.3 Private DNS Zones
Link these zones to the VNet:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

### 5.4 Network controls
- NSGs on all subnets
- Deny inbound by default
- Restrict outbound from AKS to only approved destinations
- Azure Policy to enforce:
  - no public IPs on nodes
  - private endpoint required
  - public network access disabled on PaaS
- Optional Azure Firewall for controlled egress inspection

## 6. Identity and Access Management
### 6.1 Platform access
- Microsoft Entra ID integration for AKS authentication
- Azure RBAC for Kubernetes or tightly governed Kubernetes RBAC with Entra groups
- MFA for all administrative access
- Privileged Identity Management for just-in-time elevation
- Separate roles for platform admins, cluster operators, security auditors, application deployers, and read-only support

### 6.2 Workload identity
- Use managed identities / workload identity for pods
- Do not use long-lived client secrets
- Scope identities to the minimum required:
  - Read-only access to ACR for image pull
  - Get/list only for required Key Vault secrets/certs
  - No write access unless explicitly required
  - No broad subscription or resource group permissions

### 6.3 Application Gateway identity
- Grant only the minimum permissions needed for certificate retrieval and ingress operations
- If Key Vault is used for TLS certs, the identity must have get access only, not secret management rights

## 7. Security Architecture
### 7.1 Zero trust principles
- Private-by-default for all platform services
- Deny-all egress unless explicitly allowed
- Managed identity over secrets wherever possible
- Centralized logging and auditability
- Least privilege at every layer
- No public IPs on AKS nodes
- No public network access on ACR, Key Vault, Redis, MySQL

### 7.2 Encryption policy
#### In transit
- TLS 1.2+ everywhere
- Prefer TLS 1.3 where supported
- Use mTLS internally where feasible for service-to-service trust boundaries
- Disable weak ciphers and legacy protocols

#### At rest
- AKS persistent volumes encrypted
- Redis encrypted at rest
- MySQL encrypted at rest
- ACR encrypted at rest
- Key Vault secrets/certificates encrypted at rest
- Logs and backups encrypted at rest
- Prefer customer-managed keys where supported and operationally feasible

#### Key management
- Keys stored in Key Vault with strict access control
- Key Vault public network access disabled
- Private Endpoint only
- Soft delete and purge protection enabled
- Rotation policy defined

### 7.3 WAF policy
- Application Gateway WAF v2 is the public security boundary
- WAF in Prevention mode
- OWASP CRS enabled
- Custom rules for SQL injection, XSS, bot abuse, geo/IP restrictions, and rate limiting

## 8. Application Architecture
### 8.1 Proposed logical services
1. Web Frontend / BFF
2. Customer Account Service
3. Order / Transaction Service
4. Payment Orchestration Service
5. Notification Worker
6. Read Model / Query API

### 8.2 Communication model
#### North-south traffic
- Internet → Application Gateway WAF v2 → AKS ingress controller
- TLS termination at Application Gateway or re-encryption to AKS ingress, depending on policy
- Enforce TLS 1.2+ end-to-end

#### East-west traffic
- REST/HTTPS for synchronous service-to-service calls
- Service Bus queue/topic for asynchronous workflows and retries where needed
- Redis for caching, session tokens, rate-limited ephemeral state, and distributed locks
- MySQL for system of record

### 8.3 Container security
- Pull images only from private ACR
- Enforce image scanning and signed images in CI/CD
- Use admission controls to block privileged pods, hostPath mounts, and public egress where not required
- Run containers as non-root
- Read-only root filesystem where feasible

## 9. Data Architecture
### 9.1 Azure Cache for Redis Premium
Use Redis for:
- session state
- response caching
- rate limiting counters
- short-lived distributed locks
- idempotency keys for async processing

Design notes:
- Treat Redis as ephemeral
- Do not store sensitive PCI data unless explicitly approved and encrypted at the application layer
- Use private endpoint only

### 9.2 Azure Database for MySQL Flexible Server
Use MySQL for:
- transactional system of record
- customer/account/order data
- audit metadata if appropriate

Design notes:
- Use application-level retry with exponential backoff
- Use connection pooling
- Prefer short-lived transactions
- Consider read optimization via caching rather than read replicas unless required by workload

### 9.3 Data protection
- TLS enforced
- Private Endpoint only
- Public access disabled
- Backups encrypted
- Retention aligned to PCI and business policy

## 10. Availability and Resilience
### 10.1 Availability approach
The expert reports indicate that a guaranteed 99.99% composite SLA in a single region is not realistic for this full stack. The design therefore maximizes single-region resilience in East US using zone-redundant components where supported.

### 10.2 Resilience patterns
- Multi-replica deployment for each stateless service
- Pod anti-affinity to spread replicas across nodes
- Readiness/liveness probes
- Graceful shutdown with connection draining
- Circuit breakers for downstream dependencies
- Timeouts and retries with jitter
- Bulkheads to isolate failure domains
- Idempotency keys for write operations and queue consumers

### 10.3 Scaling strategy
- Horizontal Pod Autoscaler for request-driven scaling
- Cluster autoscaling for node capacity growth
- Scale on CPU, memory, request rate, queue depth, and custom app metrics if needed

### 10.4 Failure handling
- If Redis is unavailable, degrade gracefully to direct MySQL reads where safe
- If MySQL is unavailable, fail writes fast and preserve request integrity
- Queue-based workflows should be retryable and idempotent

## 11. Ingress and Request Flow
### 11.1 Primary request flow
1. Client connects over HTTPS
2. Application Gateway WAF v2 inspects and forwards traffic
3. Traffic reaches AKS ingress controller
4. Ingress routes to BFF or API service
5. Service calls Redis/MySQL privately as needed
6. Response returns through the same path

### 11.2 Security at ingress
- WAF rules enabled for OWASP protections
- Rate limiting at edge if supported by the chosen design
- Strict host/path routing
- TLS certificates managed securely, ideally via Key Vault integration

## 12. Event-Driven Routing
Use asynchronous messaging for non-blocking workflows.

### 12.1 Recommended event flow
- API service writes to MySQL
- After commit, publish domain event to queue/topic
- Worker consumes event and performs downstream actions
- Worker updates status in MySQL and/or cache

### 12.2 Event routing principles
- At-least-once delivery
- Idempotent consumers
- Correlation IDs and causation IDs
- Dead-letter poison messages for manual review
- Separate command and event channels where useful

## 13. Deployment and Release Pattern
### 13.1 Recommended delivery model
- Blue/green or canary deployments for AKS workloads
- Progressive traffic shifting behind Application Gateway/ingress
- Automated rollback on health regression

### 13.2 CI/CD controls
- Build container images in pipeline
- Scan for vulnerabilities
- Sign images
- Push to private ACR
- Deploy via GitOps or pipeline-driven manifests
- Validate policy before promotion

## 14. Observability and Operations
### 14.1 Required telemetry
- Centralized logs
- Metrics for request latency, error rate, saturation, queue depth, Redis/MySQL dependency latency
- Distributed tracing with correlation IDs

### 14.2 Operational controls
- Alert on WAF blocks spike, 5xx increase, queue backlog growth, MySQL connection exhaustion, Redis latency spikes
- Maintain runbooks for dependency outage, deployment rollback, certificate rotation, and secret rotation

## 15. Logging and Monitoring Policy
Mandatory logs:
- AKS control plane and audit logs
- Kubernetes audit logs
- Container stdout/stderr
- Application Gateway WAF logs
- Key Vault diagnostic logs
- ACR diagnostic logs
- Redis diagnostics
- MySQL diagnostics
- NSG flow logs
- Azure Activity Logs
- Microsoft Entra sign-in and audit logs

Logging controls:
- Send all logs to a central Log Analytics workspace and/or SIEM
- Retain logs per PCI and internal retention policy
- Protect logs from tampering
- Alert on WAF blocks and anomalies, failed auth attempts, privilege escalation, secret access failures, unexpected egress, database connection spikes, pod restarts / crash loops, image pull failures, and Private Endpoint/DNS resolution failures

## 16. Compliance Notes for PCI-DSS
This design is directionally aligned with PCI-DSS, but the following must be validated in implementation:
- WAF coverage and rule tuning
- Segmentation of the cardholder data environment
- Strong authentication and MFA
- Logging completeness and retention
- Key management and rotation
- Vulnerability scanning and patching
- Secure SDLC and image scanning
- Secrets handling and certificate lifecycle
- Administrative access controls and break-glass procedures

## 17. Architecture Governance Recommendations
- Perform a PCI design review before build
- Require threat modeling for ingress, identity, secrets, and data flows
- Establish security exception handling for any service that cannot be fully private
- Validate availability assumptions against zone redundancy and dependency SLAs
- Confirm whether the Key Vault + Application Gateway certificate pattern can satisfy the no public access constraint without exception

## 18. Decision Summary
### Approved in principle
- Private AKS
- WAF ingress
- Private Endpoints for ACR, Key Vault, Redis, MySQL
- Entra ID + RBAC + managed identity
- Centralized logging and encryption controls

### Requires explicit validation
- Application Gateway certificate integration with fully private Key Vault
- Single-region availability feasibility across all dependencies
- Egress control implementation for AKS
- PCI scope confirmation for WAF and supporting services
