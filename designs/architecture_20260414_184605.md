# Technical Architecture Document

## 1. Executive Summary
Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US with:
- 10,000 requests per minute
- auto-scaling required
- 99.99% uptime target in a single region
- PCI-DSS-aligned encryption and secret handling
- no public IPs on AKS nodes
- ingress only through Application Gateway WAF v2
- all PaaS dependencies reachable only through Private Endpoints
- public network access disabled for ACR, Key Vault, Redis, and MySQL

The recommended pattern is a private AKS deployment with a public Application Gateway WAF v2 edge, private-only PaaS connectivity, managed identities, workload identity, centralized logging, and zone-aware high availability.

## 2. Scope and Assumptions
This architecture is based on the provided TOGAF, Cloud, Solution, Data, and FinOps reports. Corporate wiki validation was attempted but no internal precedent could be confirmed due to a search error.

Assumptions:
- Single-region deployment in East US
- Customer-facing application
- PCI-DSS controls apply
- Application Gateway WAF v2 is the only internet-facing ingress
- AKS nodes have no public IPs
- ACR, Key Vault, Redis, and MySQL use Private Endpoints only
- Public network access is disabled on all listed PaaS services

## 3. Target Architecture Overview
### 3.1 Edge and Ingress
- Azure Application Gateway WAF v2
- Public frontend IP
- WAF policy in prevention mode
- TLS termination at the edge
- Optional re-encryption to backend services if required by policy

### 3.2 Compute
- Private AKS cluster
- No public IPs on nodes
- System and user node pools separated
- Availability Zone spread where supported
- Cluster Autoscaler enabled
- Horizontal Pod Autoscaler enabled
- Azure Policy add-on enabled
- Azure Workload Identity enabled

### 3.3 Data and State
- Azure Cache for Redis Premium
- Azure Database for MySQL Flexible Server
- Azure Key Vault for secrets, certificates, and keys
- Azure Container Registry Premium for images

### 3.4 Network
- Dedicated East US VNet
- Separate subnets for Application Gateway, AKS, Private Endpoints, and optional management
- Private DNS zones linked to the VNet
- Egress control via approved firewall/NAT/UDR pattern

## 4. Logical Application Design
The application should use a stateless multi-tier pattern:
- Web Frontend
- Customer / Order API
- Async Worker tier

Recommended communication model:
- North-south: Internet users -> Application Gateway WAF v2 -> AKS ingress
- East-west: REST/HTTPS for synchronous calls
- Async queue/event processing for slow or non-user-critical work

Recommended service boundaries:
1. Web Frontend
2. Customer API
3. Order / Transaction API
4. Notification Worker
5. Cache Projection Worker
6. Admin / Backoffice API if needed

## 5. Security Architecture
### 5.1 Identity and Access
- Microsoft Entra ID for operators
- Kubernetes RBAC mapped to Entra groups
- Managed identities for platform access
- Azure Workload Identity for pods
- No long-lived service principal secrets
- MFA and just-in-time elevation for privileged roles

### 5.2 Network Security
- AKS nodes must not have public IPs
- Private AKS cluster or equivalent private control-plane model
- Application Gateway WAF v2 is the only public ingress
- Private Endpoints only for ACR, Key Vault, Redis, and MySQL
- Public network access disabled on all listed PaaS services
- Private DNS zones required for name resolution
- Restrict outbound traffic using explicit allow lists and egress controls

### 5.3 Container Security
- Run as non-root
- Read-only root filesystem where possible
- Drop Linux capabilities
- Disallow privileged containers
- Enforce resource requests and limits
- Use signed/scanned images from ACR
- Separate namespaces for app, system, and ops workloads

### 5.4 PCI-DSS Controls
- TLS 1.2+ everywhere
- Encryption at rest for all data services
- Secrets never stored in code or images
- Centralized audit logging
- Least privilege RBAC
- Segmentation between ingress, app, and data tiers
- Consider field-level encryption for highly sensitive payment-related data if stored

## 6. Data Architecture
### 6.1 Azure Database for MySQL Flexible Server
Use as the system of record for transactional data:
- customer records
- orders
- payment metadata references
- audit-relevant business entities

Recommended configuration:
- private access only
- public network access disabled
- private DNS zone linked to the AKS VNet
- zone-redundant HA if supported for the selected tier/region
- automated backups enabled
- point-in-time restore enabled
- encryption at rest enabled by default
- TLS 1.2+ in transit enforced

### 6.2 Azure Cache for Redis Premium
Use for:
- session storage
- distributed locks
- rate limiting
- short-lived tokens
- response caching
- idempotency keys

Recommended configuration:
- Premium tier
- Private Endpoint only
- Public network access disabled
- Persistence only if required for recovery of non-derivable cache state
- Redis is not the source of truth

### 6.3 Azure Key Vault
Use for:
- TLS certificates
- application secrets
- encryption keys
- connection secrets

Recommended configuration:
- Private Endpoint only
- Public network access disabled
- RBAC or tightly scoped access policies, not both unless documented
- Audit logging enabled

### 6.4 Azure Container Registry
Use for container images only.
Recommended configuration:
- Premium tier
- Private Endpoint only
- Public network access disabled
- Only AKS cluster identity and approved CI/CD identities may access it

### 6.5 Azure Blob Storage
Use for backups, exports, logs, and immutable artifacts if needed.
Recommended configuration:
- Private Endpoint only
- Public network access disabled
- Immutable storage / WORM if required
- Soft delete and versioning where appropriate

## 7. Network Topology
Recommended subnets:
1. AppGatewaySubnet
2. AksSubnet
3. PrivateEndpointSubnet
4. Optional ManagementSubnet or AzureBastionSubnet
5. MySQL delegated subnet if required by the chosen deployment model

Network controls:
- NSGs on workload subnets
- UDRs to force controlled egress
- No direct internet exposure to AKS nodes
- Private Link for all PaaS dependencies
- Private DNS zones for all private-link services

Private DNS zones:
- privatelink.azurecr.io
- privatelink.vaultcore.azure.net
- privatelink.redis.cache.windows.net
- privatelink.mysql.database.azure.com
- privatelink.blob.core.windows.net
- private DNS zone for private AKS API server if applicable

## 8. Availability and Scaling Strategy
### 8.1 Availability
To support 99.99% uptime in a single region:
- zone-redundant Application Gateway where supported
- AKS node pools spread across Availability Zones 1, 2, and 3
- multiple replicas for critical services
- PodDisruptionBudgets
- readiness and liveness probes
- cluster autoscaling
- managed PaaS HA settings where available

### 8.2 Scaling
10,000 requests/minute is approximately 167 requests/second average.
Design for burst capacity above average load.

Scaling mechanisms:
- Application Gateway autoscaling
- AKS Cluster Autoscaler
- Horizontal Pod Autoscaler
- Separate worker pool for async/background processing
- Redis for caching, session state, and rate limiting
- MySQL for durable transactional state

## 9. Logging and Monitoring
Centralize telemetry in Azure Monitor / Log Analytics and forward to SIEM if required.

Required logs:
- Application Gateway WAF logs
- AKS control plane logs
- AKS audit logs
- Container stdout/stderr
- Azure Activity Logs
- Key Vault diagnostics
- ACR diagnostics
- Redis diagnostics
- MySQL diagnostics
- Defender for Cloud alerts

Monitoring focus:
- WAF blocks and anomalies
- authentication failures
- secret access failures
- egress anomalies
- pod privilege escalation
- image pull failures
- database connection spikes
- Redis auth failures

## 10. Compliance and Governance
Use Azure Policy to enforce:
- no public network access on PaaS
- private endpoints required
- diagnostic settings required
- approved SKUs only
- minimum TLS versions
- private AKS cluster required

Governance controls:
- architecture review before build
- security review before production
- periodic access review
- quarterly vulnerability and configuration review
- incident response runbooks for WAF attack, secret compromise, database exposure, and image supply-chain compromise

## 11. Risk and Decision Points
Key implementation risks:
- MySQL Flexible Server networking model must be validated early
- Application Gateway to Key Vault certificate flow must be validated with the private Key Vault design
- Egress control must be explicitly designed and tested
- Single-region 99.99% remains dependent on zone support and service-specific resiliency

Must be explicitly decided:
1. Whether cardholder data is stored in the application
2. Whether TLS terminates only at App Gateway or also re-encrypts to backend
3. Whether CMK is required for all data services
4. Whether Key Vault will be used for ingress certificate lifecycle and how private-only constraints are satisfied
5. Approved egress model from AKS
6. Approved log retention period for PCI evidence

## 12. Recommended Logical Architecture Summary
- Edge: Public DNS and Application Gateway WAF v2
- AKS: Private cluster, ingress controller, web frontend pods, API pods, worker pods
- Private PaaS: ACR, Key Vault, Redis Premium, MySQL Flexible Server via Private Endpoints
- Security/Identity: Microsoft Entra Workload ID, RBAC, network policies, secretless access where possible

Proceed with a private AKS deployment in East US using:

- Centralized logging and PCI-grade encryption
