## 1. Executive Summary
This document defines the approved technical architecture for a customer-facing online storefront for a clothing brand. The solution supports product browsing, secure storage of inventory, customer accounts, and order history.

The final architecture intentionally follows the expert reports, even where they differ from the original requirement, because the reports provide the governing security, cloud, application, and data constraints. In particular, the design is a **single-region, multi-AZ Azure PaaS storefront** with **one internet-facing entry point only**: **Azure Application Gateway WAF v2**. This is a deliberate refinement of the original requirement to ensure the storefront is secure, supportable, and compliant.

## 2. Scope and Architectural Drivers
### In scope
- Public product browsing
- Customer registration and authentication
- Secure storage of inventory data
- Secure storage of customer account data
- Secure storage of order history
- Operational logging and auditability

### Key drivers
- Protect customer trust and sensitive data
- Minimize public exposure
- Enforce least privilege and strong identity controls
- Support reliable order processing and browsing performance
- Maintain auditability and recoverability

## 3. Architecture Principles
### Business principles
- Protect customer trust as a core business asset
- Minimize data collection and retention
- Ensure storefront availability and order processing continuity

### Data principles
- Customer and order data are sensitive business records
- Data classification must be defined before implementation
- Retention and deletion rules must be explicit

### Application principles
- Separate public browsing from authenticated account functions
- Use secure APIs for all data access
- Design for auditability and recoverability

### Technology governance principles
- Security controls are mandatory, not optional
- Default-deny network posture
- Centralized identity, logging, and key management

## 4. Target Solution Overview
The recommended application architecture is a **domain-driven modular architecture** with clear separation between:
- Product browsing
- Customer account management
- Inventory management
- Order processing
- Secure data storage and access control

The application should use:
- **REST APIs** for browser-facing and simple service interactions
- **Event-driven workflows** for inventory updates, order placement, and notifications
- **Queue/worker patterns** for background processing
- **CQRS** for read-heavy browsing and order history views where needed

## 5. Application Architecture
### Recommended application pattern
Start with a **modular monolith or domain-based microservices** approach rather than over-fragmenting too early.

### Suggested domains
- **Catalog Service** — product browsing, categories, pricing display
- **Customer Service** — customer profiles, authentication hooks, preferences
- **Inventory Service** — stock levels, reservations, adjustments
- **Order Service** — cart checkout, order creation, order status
- **Payment Integration Service** — external payment provider orchestration
- **Notification Service** — order confirmations, shipping updates

### Communication model
#### Synchronous
Use REST APIs for:
- Product catalog queries
- Customer account operations
- Checkout initiation
- Order status retrieval

#### Asynchronous
Use a message bus / queue-based event flow for:
- OrderPlaced
- InventoryReserved
- InventoryAdjusted
- PaymentAuthorized
- PaymentFailed
- OrderConfirmed
- OrderCancelled

### End-to-end flow
1. Customer opens storefront
2. Frontend calls Catalog API
3. Customer submits cart
4. Order Service validates request
5. Inventory Service reserves stock
6. Payment Service authorizes payment
7. Order Service finalizes order
8. Events are published for confirmation and notifications

## 6. Data Architecture
### Primary data platform
- **Azure SQL Database** for core transactional data
- **Azure Managed Redis** for low-latency caching and session/state acceleration
- **Azure Blob Storage** for product images, invoices, exports, and archival files
- **Azure Cosmos DB** is optional and future-only if global scale or schema flexibility becomes necessary

### Data domains in Azure SQL Database
1. Customer
   - customer profile
   - authentication references
   - addresses
   - consent/preferences

2. Catalog
   - product master
   - SKU variants
   - size/color attributes
   - pricing
   - inventory counts

3. Order Management
   - orders
   - order lines
   - shipment status
   - returns/refunds
   - order history

4. Inventory
   - stock ledger
   - reservations
   - adjustments
   - replenishment events

### Blob Storage domains
- product-images
- invoices
- exports
- archive

### Redis domains
- cart:{customerId}
- session:{sessionId}
- catalog:featured
- inventory:sku:{skuId}
- promo:{code}

### Replication and backup strategy
#### Azure SQL Database
- Zone redundancy enabled
- Active geo-replication or failover groups to a paired secondary region
- Read-only secondary for reporting/search-like read workloads if needed
- Automated backups with PITR, geo-restore, and LTR

#### Azure Managed Redis
- High availability enabled
- Zone redundant deployment in primary region
- Treat Redis as rebuildable state, not the system of record

#### Azure Blob Storage
- GZRS for product media and business documents
- Soft delete, versioning, and immutability policies where required

### RTO / RPO targets
| Data Domain | RTO | RPO | Notes |
|---|---:|---:|---|
| Orders / Customers / Inventory | 15–30 min | < 5 min | Core commerce data |
| Product catalog | 15 min | < 15 min | Can be rebuilt from source of truth |
| Redis cache/session | 5–15 min | Best effort | Cache can be repopulated |
| Product images / invoices | 1–4 hours | < 15 min | Depends on storage replication and restore path |

## 7. Cloud Infrastructure Architecture
### Target Azure services
#### Internet-facing edge
- **Azure Application Gateway WAF v2**
  - Public frontend IP
  - TLS termination
  - WAF policy enabled
  - Routes only to private App Service backend

#### Application tier
- **Azure App Service**
  - Hosts storefront web app and API
  - Public network access disabled
  - Integrated with VNet for outbound private access
  - No public IPs on app workers

#### Data tier
- **Azure SQL Database**
  - Private Endpoint enabled
  - Public network access disabled

#### Cache
- **Azure Cache for Redis**
  - Private Endpoint enabled
  - Public network access disabled

#### Secrets and certificates
- **Azure Key Vault**
  - TLS cert for Application Gateway
  - App secrets and connection strings
  - Private Endpoint enabled
  - Public network access disabled

#### Optional storage
- **Azure Storage Account**
  - Product images, static assets, exports, backups if needed
  - Private Endpoint enabled
  - Public network access disabled

#### Monitoring
- **Azure Monitor + Log Analytics**
  - Centralized logs, metrics, alerts

### Network topology
#### Virtual Network
- VNet: `vnet-storefront-prod`
- Address space: `10.40.0.0/16`

#### Subnets
1. `snet-appgw` — `10.40.0.0/24`
2. `snet-appsvc-integration` — `10.40.1.0/24`
3. `snet-private-endpoints` — `10.40.2.0/24`
4. `snet-management` — `10.40.3.0/24`

### Private DNS zones
- `privatelink.azurewebsites.net`
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.blob.core.windows.net`

### Explicit security posture
- Only Application Gateway is internet-facing
- App Service public network access is disabled
- No public IPs are assigned to application workers or data services
- Azure SQL public network access is disabled
- Key Vault public network access is disabled
- Redis public network access is disabled
- Storage public network access is disabled
- All service-to-service traffic uses Private Link

## 8. Security, IAM, Logging, and Compliance
### IAM requirements
- Least privilege
- No shared accounts
- MFA for all privileged users and internal administrative access
- Role-based access control for customer, support, inventory, fulfillment, service identity, audit reviewer, and platform administrator
- Just-in-time elevation for admin access
- Quarterly access reviews
- Unique non-human identity for each application component
- No embedded secrets in code or configuration files

### Logging and monitoring requirements
- Centralized logging for authentication, authorization, admin actions, data changes, and security events
- Capture login success/failure, MFA events, password resets, account creation/deletion, order changes, inventory adjustments, privilege changes, configuration changes, API failures, and suspicious patterns
- Tamper-resistant logs with controlled access and retention
- Alerts for repeated failed logins, privilege escalation, unusual inventory changes, mass order modifications, and suspicious data export activity
- Do not log secrets, full payment data, or unnecessary personal data

### Encryption requirements
- TLS 1.2+ for all external and internal service communications
- HSTS for public web traffic where applicable
- Encryption at rest for all customer, order, and inventory data
- Backups and replicas encrypted
- Centralized key management with rotation
- Separation of duties between key administrators and data administrators
- Minimize storage of sensitive personal data
- Tokenize or redact where possible
- Do not store payment card data unless explicitly required and PCI scope is accepted

### Compliance considerations
Potentially relevant standards and regulations:
- CIS Benchmarks
- NIST guidance
- GDPR / CCPA or similar privacy laws
- PCI DSS if cardholder data is stored, processed, or transmitted directly

Recommended stance: avoid storing card data unless there is a strong business reason and formal PCI scope is accepted.

## 9. Reliability, Availability, and Operations
### Availability controls
- Application Gateway WAF v2 deployed zone-redundant
- App Service deployed with at least 2–3 instances
- Azure SQL Database zone-redundant where supported
- Redis configured for high availability
- Private Endpoints reduce exposure and support stable internal connectivity

### Scalability controls
#### App Service autoscale
- Minimum: 2 instances
- Scale out based on CPU, memory, and latency thresholds
- Maximum instance count based on budget and load testing

#### SQL scaling strategy
- Start with a service tier sized for expected order volume
- Use vertical scaling for growth
- Consider read replicas or elastic patterns later if needed

#### Redis sizing
- Use Redis as session store, product catalog cache, and cart cache
- Define eviction policy based on cache-first behavior
- Size for peak browse traffic and checkout bursts

#### Queue-based decoupling
For future growth, add Azure Service Bus for checkout/order fulfillment events and async processing for order confirmation, inventory updates, email notifications, and fulfillment integration.

### Operational excellence
- Application Insights for App Service
- Azure Monitor alerts for 5xx rate, latency, CPU/memory saturation, SQL pressure, Redis memory pressure, and WAF blocked requests
- Log Analytics workspace for centralized logs
- Blue/green or deployment slots for App Service
- Infrastructure as Code via Bicep or Terraform
- Runbooks for WAF false positives, SQL failover, Redis rebuild, private endpoint/DNS failures, and certificate renewal
