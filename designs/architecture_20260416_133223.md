# 1. Overview
This document defines the technical architecture for a corporate blog and news portal. The solution is intentionally simple and production-ready: a public website for readers, a content management experience for the marketing team, and a secure relational database for articles, author profiles, and reader comments.

The final design reflects the expert reports, which take precedence over the original requirement where needed. In particular, the architecture uses Azure PaaS services, a WAF-protected public entry point, private connectivity to data services, centralized identity, and strong logging and encryption controls.

# 2. Scope and Design Principles
## In scope
- Public website for article consumption
- Authoring and publishing workflow for marketing users
- Comment submission and moderation
- Secure storage of article text, author profiles, and comments
- Security, compliance, logging, encryption, and network isolation

## Out of scope
- Physical infrastructure design
- Exact instance counts and deployment mechanics
- Custom multi-region topology unless later required by business continuity needs

## Design principles
- Keep the solution simple and maintainable
- Use PaaS-first Azure services
- Enforce least privilege and separation of duties
- Protect public endpoints with WAF and HTTPS
- Keep the database private and accessible only from the application tier
- Centralize secrets, logs, and identity

# 3. Business and Architecture Rationale
The original requirement asked for a simple website and database. The expert reports refine that requirement by adding mandatory governance controls. As a result, the architecture is still simple, but it is not a bare-bones deployment. It includes:
- Azure Application Gateway with WAF for internet ingress
- Azure App Service for the web and application tier
- Azure SQL Database for structured content and workflow data
- Azure Key Vault for secrets
- Private Endpoints and private DNS for secure service access
- Optional Azure Blob Storage and Azure Cache for Redis for media and performance

This change is justified because the portal is public-facing and will store user-generated content, which materially increases security and compliance risk.

# 4. Logical Architecture
## 4.1 User groups
- **Public Readers**: anonymous visitors who read published content
- **Commenters**: authenticated users who submit comments
- **Authors**: marketing users who create and edit drafts
- **Editors**: users who approve and publish content
- **Moderators**: users who manage comments and abuse reports
- **Platform Admins**: technical administrators with limited platform control
- **Security Auditors**: read-only access to logs and audit trails

## 4.2 Application components
- **Public Website**: renders article pages, author pages, and comment sections
- **Content Management UI**: used by marketing to draft, edit, and publish content
- **Backend Application**: validates input, enforces workflow, and exposes APIs
- **Database**: stores articles, authors, comments, moderation actions, and audit metadata

## 4.3 Data entities
- Article
- Author
- Comment
- Category/Tag
- AuditLog
- ModerationAction
- PublishEvent

# 5. Azure Reference Architecture
## 5.1 Core services
- **Azure App Service**: hosts the website and application logic
- **Azure SQL Database**: system of record for content and workflow data
- **Azure Key Vault**: stores secrets, certificates, and connection strings
- **Azure Application Gateway v2 with WAF**: public entry point and web protection
- **Azure Blob Storage**: stores images, attachments, and optional large content assets
- **Azure Cache for Redis**: caches hot content and ephemeral state

## 5.2 Network topology
A single VNet is used for simplicity:
- **VNet**: `vnet-blog-prod`
- **Address space**: `10.20.0.0/16`

### Subnets
- **`snet-appservice-integration`**: `10.20.1.0/24`
- **`snet-private-endpoints`**: `10.20.2.0/24`
- **`snet-appgw`**: `10.20.3.0/24`

## 5.3 Private DNS zones
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`

## 5.4 Connectivity pattern
- Public users connect to Application Gateway over HTTPS
- Application Gateway forwards traffic to App Service
- App Service uses managed identity and private endpoints to reach SQL and Key Vault
- Blob Storage and Redis are accessed privately where enabled
- Database is not publicly accessible

# 6. Security Architecture
## 6.1 Identity and access management
- Use centralized enterprise identity only
- Require SSO with Microsoft Entra ID or equivalent
- No shared accounts
- Enforce MFA for privileged users and remote access
- Use RBAC and least privilege
- Separate content creation, approval, and platform administration duties
- Use just-in-time elevation where possible
- Disable local/basic authentication for admin interfaces
- Review access quarterly and on role change/offboarding

## 6.2 Logging and monitoring
Capture at minimum:
- Authentication success/failure
- MFA challenges and failures
- Content create/update/delete/publish actions
- Comment create/edit/delete/moderation actions
- Role assignment changes
- Configuration changes
- Secret access events
- Database administrative actions
- Security policy violations
- Suspicious request patterns and WAF events

Logging standards:
- Centralize logs in SIEM
- Protect logs from tampering
- Synchronize time sources
- Retain logs per corporate policy
- Do not store secrets or full sensitive payloads in logs

## 6.3 Encryption
### In transit
- HTTPS only
- TLS 1.2 or higher, prefer TLS 1.3
- Encrypt service-to-service traffic

### At rest
- Encrypt SQL Database, Blob Storage, and backups
- Use customer-managed keys if required by policy
- Store secrets only in Key Vault

## 6.4 Network isolation
- Database must not be publicly accessible
- Restrict database access to the application tier only
- Use private network connectivity between app and data services
- Isolate admin interfaces from public access
- Restrict outbound traffic to approved destinations
- Place the site behind WAF and DDoS protection as needed

# 7. Data Architecture
## 7.1 Data classification
- **Public**: published articles
- **Internal**: drafts, editorial notes, operational metadata
- **Confidential / Personal Data**: author profiles, user accounts, reader comments if they contain personal data

## 7.2 Data services
### Azure SQL Database
Primary system of record for:
- author profiles
- article metadata
- publishing workflow state
- reader comments
- moderation/audit records

### Azure Blob Storage
Used for:
- images and media
- attachments
- optional archived article snapshots

### Azure Cache for Redis
Used for:
- hot article pages
- author profile lookups
- comment counts
- ephemeral session/state data

## 7.3 Data retention and deletion
- Define retention periods for drafts, published content, comments, and moderation records
- Support deletion or anonymization where legally required
- Preserve legal hold capability for investigations

# 8. Application and Workflow Design
## 8.1 Publishing workflow
1. Author creates or edits a draft
2. Backend validates and stores the draft
3. Editor reviews and approves content
4. Content is published
5. Public site displays published content only

## 8.2 Comment workflow
1. Reader submits a comment
2. Backend stores it as pending
3. Moderator reviews the comment
4. Approved comments become visible publicly

## 8.3 API style
- Use synchronous REST APIs over HTTPS
- Keep the application modular monolith or small service-based design
- Avoid unnecessary distributed complexity

# 9. Availability, Backup, and Recovery
## 9.1 Availability approach
- Start with a single App Service plan
- Enable autoscale if traffic grows
- Use zone-redundant options where available
- Consider geo-redundant backups for SQL if business continuity requirements increase

## 9.2 Backup strategy
### Azure SQL Database
- Automated backups
- Point-in-time restore
- Geo-restore or failover groups if needed
- Long-term retention if required

### Azure Blob Storage
- Soft delete
- Versioning
- Storage redundancy appropriate to business needs

### Redis
- Treat as disposable cache
- Do not rely on it for durable state

## 9.3 RTO / RPO targets
- SQL Database RPO: < 5 minutes
- Blob Storage RPO: near-zero to < 15 minutes depending on redundancy
- RTO for primary region disruption: < 1 hour
- RTO for database restore: 1–2 hours
- Cache recovery: minutes

# 10. Compliance and Control Alignment
This portal should align to:
- CIS Controls
- NIST-aligned principles
- Internal standards for identity lifecycle management, secure SDLC, vulnerability management, incident response, and data retention/privacy

# 11. Key Architecture Decisions
1. **Use Azure App Service** rather than custom VMs to reduce operational burden.
2. **Use Azure SQL Database** because the workload is relational and transactional.
3. **Use Azure Application Gateway with WAF** because the site is public-facing.
4. **Use private endpoints and private DNS** to keep data services off the public internet.
5. **Use Azure Key Vault** for secrets and certificates.
6. **Use centralized identity and RBAC** to enforce separation of duties.
7. **Use logging and audit trails** to support investigations and compliance.
8. **Use Blob Storage and Redis optionally** for media and performance, not as system of record.

# 12. Final Architecture Summary
The recommended solution is a secure, simple Azure PaaS architecture for a corporate blog and news portal:
- Public traffic enters through **Azure Application Gateway WAF v2**
- The application runs on **Azure App Service**
- Content and comments are stored in **Azure SQL Database**
- Secrets are stored in **Azure Key Vault**
- Media and optional large content are stored in **Azure Blob Storage**
- Performance caching is handled by **Azure Cache for Redis**
- Private endpoints, private DNS, centralized logging, and strong IAM controls protect the platform
