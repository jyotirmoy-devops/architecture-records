# Technical Architecture Document

## 1. Purpose
This document defines the technical architecture for a new corporate blog and news portal. The solution supports marketing-authored article publishing, author profile management, and reader comments, with safe persistent storage for all content.

## 2. Requirement Interpretation
The original requirement asked for a simple website and database. The expert reports refine that request into a secure, production-ready corporate content platform with explicit controls for public exposure, user-generated content, and administrative publishing.

Where the original requirement was ambiguous, the expert reports take precedence. In particular, the design is intentionally more controlled than a minimal website because the portal is public-facing and stores personal and editorial data.

## 3. Architecture Summary
Recommended architecture style:
- Modular Monolith application backend
- CRUD + content publishing workflow
- Web-Queue-Worker pattern for asynchronous tasks
- REST APIs for synchronous interactions
- Message bus / queue for background side effects

This keeps the solution simple while still supporting moderation, notifications, indexing, and audit logging.

## 4. Business and Functional Scope
The portal must support:
- Public article browsing
- Author profile pages
- Reader comments
- Marketing/editor publishing workflow
- Comment moderation
- Auditability of content changes

## 5. Security and Compliance Drivers
The design must address:
- Public internet exposure
- User-generated content risks
- Privileged publishing access
- Personal data handling
- Spam, injection, and account takeover risks
- Logging, encryption, and network isolation requirements

## 6. Application Architecture
### 6.1 Logical Modules
The application is organized into the following modules:

**Public Content Module**
- Article listing
- Article detail pages
- Category/tag browsing
- Author profile pages

**Editorial Module**
- Create/edit/delete articles
- Draft/publish workflow
- Scheduling posts
- Managing author bios and profile images

**Comments Module**
- Reader comment submission
- Comment moderation
- Spam filtering
- Comment visibility rules

**Identity and Access Module**
- Marketing team login
- Role-based access control
- Editor/admin permissions

**Background Processing Module**
- Notifications
- Previews
- Search indexing
- Moderation queue processing

### 6.2 Communication Patterns
**Synchronous communication**
- REST APIs between frontend and backend
- REST APIs for editorial UI, author/profile management, comment submission, and moderation actions

**Asynchronous communication**
- Message queue / service bus for moderation jobs, notification emails, search indexing, publish events, and analytics/event tracking

### 6.3 Event-Driven Flows
**ArticlePublished**
- Trigger search indexing
- Trigger cache refresh
- Trigger notification workflow

**CommentSubmitted**
- Trigger moderation workflow
- Trigger spam detection
- Optionally notify moderators

**AuthorProfileUpdated**
- Refresh public profile pages
- Update cached content

## 7. Data Architecture
### 7.1 System of Record
Use **Azure SQL Database** as the system of record for structured content and workflow data.

Store in SQL:
- Authors
- Articles
- ArticleRevisions
- Comments
- ModerationFlags
- PublishingAudit

### 7.2 Media and Rich Content Storage
Use **Azure Blob Storage** for:
- Article images
- Hero banners
- Attachments
- Optional exports and archived content

### 7.3 Cache Layer
Use **Azure Cache for Redis** for:
- Cached article pages
- Cached article lists and category pages
- Short-lived moderation/session data if required

## 8. Azure Infrastructure Architecture
### 8.1 Edge and Web Tier
- **Azure Front Door Premium**
- WAF policy in Prevention mode
- OWASP managed rules enabled
- Rate limiting enabled
- Bot protection enabled where appropriate
- Public ingress only through Front Door

### 8.2 Application Tier
- **Azure App Service Plan Standard S1**
- **Azure App Service Web App**
- No VM-based nodes
- No public IPs on nodes
- Public inbound access only through Front Door
- Managed Identity for Azure service access

### 8.3 Data and Supporting Services
- **Azure SQL Database General Purpose Serverless**
- **Azure Storage Account GPv2 Hot LRS**
- **Azure Cache for Redis Standard C1**
- **Azure Key Vault Standard**

### 8.4 Network Topology
**Virtual Network:** `vnet-corp-blog-prod`  
**Address space:** `10.20.0.0/16`

**Subnets**
1. `snet-appsvc-integration` — `10.20.1.0/26`  
   Delegation: `Microsoft.Web/serverFarms`
2. `snet-private-endpoints` — `10.20.2.0/27`  
   Purpose: private endpoints for SQL, Key Vault, Storage, and Redis
3. `snet-management` — `10.20.3.0/27`  
   Purpose: future admin tooling only

**Private Endpoints**
- Azure SQL Database
- Azure Key Vault
- Azure Storage Blob
- Azure Cache for Redis

**Private DNS Zones**
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`
- `privatelink.blob.core.windows.net`
- `privatelink.redis.cache.windows.net`

## 9. Security Architecture
### 9.1 Mandatory Controls
- No public IPs on nodes
- Public network access disabled for SQL, Storage, Key Vault, and Redis
- Private endpoints mandatory for all backend services
- Managed Identity only for application access to Azure services
- HTTPS only for all public traffic
- TLS 1.2 minimum
- MFA required for privileged administrative access

### 9.2 Edge Protection
- Azure Front Door Premium
- WAF in Prevention mode
- OWASP managed rules
- Rate limiting
- Bot protection where appropriate

### 9.3 Data Protection
- SQL encryption at rest enabled
- Storage encryption at rest enabled
- Key Vault used for secrets and keys
- Backups encrypted
- Private DNS used for all private endpoint name resolution

## 10. IAM and Access Control
Required roles:
- Anonymous Reader
- Commenter
- Author
- Editor/Marketing Publisher
- Administrator
- Security/Audit Reader

Authentication requirements:
- Corporate SSO for internal users
- MFA for privileged roles
- No shared accounts
- Time-bound break-glass access

Authorization requirements:
- Separate permissions for draft, review, publish, delete
- Separate permissions for comment moderation
- No direct database access for marketing users
- Break-glass admin access must be time-bound and audited

## 11. Logging and Audit Policy
Log at minimum:
- Login success/failure
- MFA events
- Content create/update/delete/publish actions
- Comment moderation actions
- Permission changes
- Configuration changes
- Database administrative actions
- Security events and blocked requests

Log protection requirements:
- Centralized, immutable log storage
- Restricted access to logs
- Time synchronization across systems
- Retention aligned to corporate policy and regulatory needs
- Alerting on suspicious admin activity, repeated failures, and content tampering

## 12. Encryption Policy
### 12.1 In Transit
- TLS 1.2+ required for all external and internal application traffic
- HTTPS only for public access
- No plaintext admin or database connections

### 12.2 At Rest
- Encrypt the database at rest using approved enterprise-managed keys
- Encrypt backups and exports
- Encrypt any file attachments or media storage if used

### 12.3 Key Management
- Keys must be managed through approved enterprise key management services
- Key rotation policy must be defined
- Access to keys must be restricted and audited
- Separate duties between application operators and key administrators

## 13. Data Governance
- Classify article content, author profiles, and comments according to corporate data classification
- Define retention periods for comments and author records
- Support deletion/anonymization workflows for privacy requests
- Establish moderation and takedown procedures
- Prevent storage of sensitive personal data in comments where possible

## 14. Reliability and Availability
- SQL automated backups and point-in-time restore
- Storage soft delete and versioning
- Redis treated as a production cache with a resilient tier
- Single-region design is acceptable for a simple portal
- RTO target: 1 hour
- RPO target: 15 minutes

## 15. TOGAF Architecture Implications
### Business Architecture
- Marketing needs a simple publishing workflow
- Moderation and approval must be explicit
- Ownership of content lifecycle must be defined

### Data Architecture
- Separate content, identity, and audit data domains
- Define master data for authors
- Define retention and deletion rules for comments

### Application Architecture
- CMS or custom app must support RBAC, audit logging, and moderation
- Comment subsystem should be isolated logically from publishing workflows
- Admin functions must be separated from public-facing functions

### Technology Architecture
- Use approved managed services where possible
- Enforce encryption, logging, and network segmentation
- Apply secure configuration baselines and patch management

## 16. Recommended Decision Gates Before Build
1. Confirm internal wiki standards and prior incidents
2. Confirm data classification and retention requirements
3. Confirm whether comments are required at launch
4. Confirm SSO/MFA integration approach
5. Confirm logging and audit retention requirements
6. Confirm privacy/legal review for public comments and author profiles

## 18. Final Recommendation
Approve the design with these mandatory rules:
1. No public IPs on nodes
2. Blob Storage private access is mandatory
3. Redis must be Standard C1 or higher
4. Disable public network access on SQL, Storage, Key Vault, and Redis
5. Use private endpoints and private DNS for all backend services
6. Use Managed Identity only for application access to Azure services

## 19. Why the Original Requirement Was Altered
The original request described a simple website and database. The expert reports require a more secure and compliant implementation because the portal is public-facing, stores personal data, and includes user-generated content and administrative publishing rights. Therefore, the architecture was expanded to include WAF protection, private endpoints, centralized logging, encryption, RBAC, and managed identity-based access.
