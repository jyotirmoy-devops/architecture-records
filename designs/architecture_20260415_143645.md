# Technical Architecture Document

## 1. Executive Summary
This architecture delivers a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) with PCI-DSS-aligned controls, private-only PaaS connectivity, and autoscaling for approximately 10,000 requests per minute.

The final design is **multi-region**, not single-region, because the Cloud Infrastructure Report explicitly states that a **99.99% SLA cannot be accepted as a single-region design** and requires a **global traffic manager such as Azure Front Door**. Per the override instruction, the expert reports take precedence over the original requirement. The original single-region East US requirement was therefore altered to satisfy the reliability gate while preserving the security constraints.

## 2. Architecture Drivers
### Functional
- Customer-facing web application
- 10,000 requests per minute
- Autoscaling required
- Stateful dependencies: Redis Premium and MySQL Flexible Server

### Non-Functional
- 99.99% uptime target
- PCI-DSS encryption standards
- No public IPs on AKS nodes
- Ingress only through Application Gateway WAF v2
- All PaaS services must have public network access disabled
- Private Endpoints only for ACR, Key Vault, Redis, and MySQL

### Compliance and Security
- Microsoft Entra ID integration
- MFA and Conditional Access
- Least privilege RBAC
- Managed identities only
- Private logging via AMPLS
- TLS 1.2+ everywhere

## 3. Requirement Override and Rationale
The original requirement requested a **single-region East US** deployment with **99.99% uptime**. The Cloud Infrastructure Report explicitly rejects that as insufficient for the stated SLA and recommends a **multi-region active-active or active-passive design** with **Azure Front Door Premium**.

### Why the original requirement was altered
- A single-region design does not satisfy the reliability gate for 99.99% availability.
- The expert report states that Microsoft guidance favors global traffic management for this SLA.
- The corrected design preserves the security constraints while improving resilience.

## 4. Target-State Architecture
### 4.1 Global Entry and Traffic Flow
1. Customer traffic enters **Azure Front Door Premium**.
2. Front Door performs **global WAF inspection**.
3. Traffic routes to the healthiest regional origin:
   - East US Application Gateway WAF v2
   - Secondary region Application Gateway WAF v2
4. Application Gateway forwards traffic to the regional **private AKS ingress**.
5. AKS services access:
   - Azure Cache for Redis Premium
   - Azure Database for MySQL Flexible Server
   - Azure Key Vault
   - Azure Container Registry
   through **Private Endpoints only**.

### 4.2 Availability Model
Preferred model:
- **Active-active across two regions**

Alternative model:
- **Active-passive with warm standby**

For the stated SLA, active-active is the stronger fit.

## 5. Azure Services
### 5.1 Edge and Ingress
- **Azure Front Door Premium**
  - Global routing
  - WAF
  - Health probes
  - Origin failover
- **Application Gateway WAF v2**
  - One per region
  - Autoscaling
  - Zone redundant where available
  - Public frontend only if required for regional origin exposure; otherwise use private origin patterns where supported

### 5.2 Compute
- **Azure Kubernetes Service**
  - Private cluster
  - No public node IPs
  - System and user node pools
  - Cluster Autoscaler
  - HPA
  - PodDisruptionBudgets
  - Azure CNI
  - Network Policies

### 5.3 Data and Platform Services
- **Azure Cache for Redis Premium**
- **Azure Database for MySQL Flexible Server**
- **Azure Container Registry Premium**
- **Azure Key Vault**

All of the above must have:
- Public network access disabled
- Private Endpoint only
- Private DNS zone integration

## 6. Network Topology
### 6.1 Hub-Spoke per Region
Use a **regional hub-spoke** model in each Azure region.

### 6.2 Subnets per Region
- `snet-appgw`
- `snet-aks-system`
- `snet-aks-user`
- `snet-private-endpoints`
- `snet-bastion`
- `snet-firewall` if egress inspection is required

### 6.3 Private DNS Zones
Link these zones to each workload VNet:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`
- AKS private cluster DNS zone as provisioned by Azure

## 7. Key Security Decision
The certificate pattern must be changed to avoid the unresolved risk.

### Recommended pattern
- Store the TLS certificate in **Azure Key Vault**
- Use **managed identity** for Application Gateway access
- Validate that the certificate retrieval path works with **Key Vault private endpoint + private DNS**
- If operationally blocked, use an approved certificate automation process that still preserves private-only access

Microsoft Learn confirms that Application Gateway v2 supports Key Vault integration for TLS certificates, and that private endpoint access to Key Vault is supported when the private DNS zone is linked correctly.

## 8. Reliability Rationale
Microsoft guidance for reliability states:
- Single-region deployments are not sufficient for mission-critical high availability targets
- Azure Front Door is the recommended global routing service for active-active or active-passive multi-region designs
- AKS multi-region deployment models also recommend Front Door in front of regional origins

Therefore, the corrected design includes:
- At least two regions
- Global traffic routing
- Health-based failover

## 9. Compliance Notes
This design supports PCI-DSS expectations by enforcing:
- TLS 1.2+
- WAF at the edge
- Private-only PaaS access
- Managed identities
- Least privilege RBAC
- Encryption at rest and in transit
- Centralized logging and auditability

## 10. Application and Solution Architecture
### 10.1 Recommended Application Pattern
Use a **modular monolith or well-bounded microservices** approach depending on team size and release cadence.

Preferred pattern:
- Web-Queue-Worker for non-blocking or long-running work
- CQRS-lite for read-heavy customer-facing endpoints if read/write paths diverge
- Stateless API services behind AKS ingress
- Event-driven async processing for email, payment orchestration, audit logging, and cache refresh

### 10.2 Suggested Service Boundaries
1. Web Frontend
   - Serves customer UI
   - Calls backend APIs over HTTPS
   - No direct access to data stores

2. API Service
   - Primary business API
   - Handles authentication, authorization, validation, and orchestration
   - Reads/writes MySQL for transactional data
   - Uses Redis for caching, session state, rate limiting, and short-lived tokens

3. Worker Service
   - Processes async jobs from a queue
   - Handles notifications, report generation, reconciliation, and other background tasks
   - Can also perform cache invalidation and downstream integration

4. Admin/Backoffice API
   - Separate logical boundary from customer-facing APIs
   - Stronger authorization controls
   - Optional if operational needs exist

### 10.3 Communication Pattern Between Compute Instances
North-south traffic:
- Client → Application Gateway WAF v2 → AKS Ingress Controller → API pods
- Protocol: HTTPS only

East-west traffic inside AKS:
- Service-to-service REST over HTTPS for synchronous calls
- Queue-based messaging for asynchronous work
- Optional gRPC only for internal high-throughput service calls if needed

Async communication:
- Use a service bus / queue abstraction for decoupling web requests from background processing
- If keeping the design strictly within the listed services, the application can still implement a queue-backed worker pattern using an internal message broker abstraction; however, for Azure-native reliability, a managed queue is strongly preferred

## 11. Security Architecture
### 11.1 Network Isolation
- AKS nodes: no public IPs
- AKS cluster: private networking only
- All PaaS services:
  - ACR
  - Key Vault
  - Redis Premium
  - MySQL Flexible Server
  must have:
  - Public network access disabled
  - Private Endpoint only
- Use private DNS zones for name resolution of all private endpoints

### 11.2 Ingress Security
- Application Gateway WAF v2 is the only public entry point
- WAF policy should enforce:
  - OWASP protections
  - request size limits
  - geo/IP restrictions if required
  - bot and anomaly protections where applicable
- TLS termination at App Gateway, then re-encrypt to AKS ingress/backend

### 11.3 Identity and Secrets
- Use managed identity for AKS workloads where possible
- Pull secrets from Key Vault via CSI driver or workload identity
- No secrets in container images, manifests, or environment variables unless unavoidable

### 11.4 PCI-DSS Controls
- Enforce TLS 1.2+ end-to-end
- Encrypt data at rest using platform encryption
- For sensitive application data, use application-level encryption for fields that require stronger PCI handling
- Minimize cardholder data storage; tokenize where possible
- Centralize audit logging and access logging

## 12. Availability and Scaling Design
### 12.1 Availability Target
To achieve 99.99% in a single region was the original request, but the corrected design uses multi-region resilience. The architecture should still be zone-aware in each region:
- Multiple AKS node pools across availability zones where available
- Multiple replicas for all stateless services
- PodDisruptionBudgets
- Readiness/liveness probes
- Graceful shutdown and connection draining
- MySQL HA configuration
- Redis Premium with zone-redundant or high-availability configuration where supported

### 12.2 Autoscaling
- Horizontal Pod Autoscaler for API and worker pods
- Cluster autoscaling for node capacity
- Scale on:
  - CPU
  - memory
  - request rate
  - queue depth
  - custom app metrics if needed

### 12.3 Capacity Guidance
10,000 requests/minute is about 167 requests/second.
With caching and stateless APIs, this is a good fit for AKS autoscaling, assuming:
- efficient API handlers
- connection pooling to MySQL
- aggressive cache usage for read-heavy paths

## 13. Data and State Design
### 13.1 Azure Cache for Redis Premium
Use for:
- response caching
- session state if required
- distributed locks sparingly
- rate limiting counters
- short-lived tokens and idempotency keys

Rules:
- Do not treat Redis as the system of record
- Set TTLs for all cache entries
- Invalidate on write events where needed

### 13.2 Azure Database for MySQL Flexible Server
Use for:
- transactional application data
- user profiles
- orders/payments metadata
- audit references

Rules:
- Use connection pooling
- Use least-privilege DB users
- Encrypt sensitive columns at the application layer if required by PCI scope
- Backups and point-in-time restore should be enabled

## 14. Recommended Request Flow
### 14.1 Customer Request Path
1. Customer browser hits public DNS
2. Traffic lands on Application Gateway WAF v2
3. WAF forwards to AKS ingress
4. Ingress routes to API service
5. API service:
   - validates auth
   - checks Redis cache
   - queries MySQL if needed
   - writes transactional data
   - emits async work if required
6. Worker service processes queued tasks
7. API returns response to client

### 14.2 Example Async Flow
- Order placed
- API writes order to MySQL
- API publishes event/job
- Worker sends confirmation email, updates cache, and performs downstream processing

## 15. Container and Supply Chain Security
- Store images in ACR with private endpoint only
- Use signed, scanned images
- Enforce admission controls for:
  - approved registries only
  - non-root containers
  - read-only root filesystem where possible
  - resource limits required
- Run vulnerability scanning in CI/CD
- Use immutable image tags or digests in deployment manifests

## 16. Observability and Operations
Implement:
- centralized application logs
- WAF logs
- AKS audit logs
- MySQL and Redis diagnostics
- distributed tracing
- metrics for:
  - request latency
  - error rate
  - saturation
  - cache hit ratio
  - DB connection pool usage
  - queue depth
  - pod restarts

Operational requirements:
- alert on WAF blocks, auth failures, DB latency, cache misses, and pod crash loops
- define SLOs for API latency and availability
- use correlation IDs across all services

## 17. Governance and Policy Enforcement
Implement Azure Policy to enforce:
- Public network access disabled on:
  - ACR
  - Key Vault
  - Redis
  - MySQL
- Private Endpoint required for each PaaS service
- AKS private cluster configuration
- No public IPs on node pools
- TLS minimum version enforcement
- Diagnostic logs enabled for all services

## 19. Key Design Decisions
- Pattern: Stateless API + Web-Queue-Worker + CQRS-lite
- Ingress: Application Gateway WAF v2 only
- Compute communication: HTTPS REST for sync, queue-based async for background work
- Data: MySQL as system of record, Redis as cache/state accelerator
- Security: Private Endpoints only for all PaaS, no public access, managed identity, Key Vault-backed secrets
- Availability: multi-replica, autoscaling, zone-aware deployment, PDBs, health probes

## 20. Final Recommendation
This application should be built as a **private, zero-trust AKS-hosted web platform** with:
- public edge only at Application Gateway WAF v2
- private-only service access to all PaaS
- stateless application tiers
- async processing for non-critical work
- strong encryption and secret management for PCI-DSS alignment

The final architecture is intentionally multi-region to satisfy the 99.99% availability requirement as corrected by the expert reports.
