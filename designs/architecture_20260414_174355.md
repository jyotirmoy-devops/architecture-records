# Technical Architecture Document

## 1. Executive Summary
Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US with:
- 10,000 requests per minute
- autoscaling at pod and node levels
- 99.99% uptime target in a single region
- PCI-DSS-aligned encryption and secret handling
- no public IPs on AKS nodes
- ingress only through Application Gateway WAF v2
- Azure Cache for Redis Premium and Azure Database for MySQL Flexible Server
- all PaaS dependencies isolated via Private Endpoints only
- no public network access on ACR, Key Vault, Redis, or MySQL

This design uses a private AKS cluster, layered ingress security, and a queue-based asynchronous processing pattern for non-user-facing work to protect the application from traffic spikes and improve resilience.

## 2. Corporate Wiki / Internal Standards Check
I attempted to search the corporate wiki for preferred patterns and internal standards, but the wiki search endpoint was unavailable. No internal standards could be confirmed from the wiki during this design pass.

Given that, the design below follows widely accepted Azure application architecture patterns for secure regulated workloads.

## 3. Recommended Application Patterns
### Core patterns
- Microservices or modular monolith with clear bounded contexts
- CQRS for read-heavy or latency-sensitive user views
- Web-Queue-Worker
- Event-driven integration
- Idempotent consumers
- Circuit breaker / retry / timeout policies

### Security patterns
- Zero-trust internal communication
- Secrets externalized
- Private-by-default networking
- Defense in depth

## 4. Logical Application Boundary Design
### A. Web Frontend / API Gateway Layer
- Public entry point is Application Gateway WAF v2
- Responsibilities:
  - TLS termination
  - WAF inspection
  - Path-based routing
  - Optional header normalization
  - Rate limiting / bot mitigation via WAF policy where applicable

### B. AKS Application Layer
Inside AKS, split workloads into these logical services:
1. Web/BFF service
2. Core business API services
3. Worker services
4. Read model/query service
5. Audit/telemetry publisher

## 5. Communication Model
### External traffic
- Internet users → Application Gateway WAF v2 → AKS ingress
- HTTPS only
- TLS 1.2+
- Prefer end-to-end encryption from gateway to backend where feasible

### Internal service-to-service
- REST/JSON for simple synchronous APIs
- gRPC for high-throughput internal service calls where low latency matters
- Service Bus queues/topics for asynchronous work and decoupling
- Internal events for state changes and integration

### Data access
- AKS → MySQL Flexible Server over Private Endpoint
- AKS → Redis Premium over Private Endpoint
- AKS → Key Vault over Private Endpoint
- AKS → ACR over Private Endpoint

## 6. Network and Ingress Design
- Application Gateway WAF v2 is the only public entry point
- Route traffic to AKS via private backend connectivity
- Use host-based routing and path-based routing
- AKS cluster should be private
- No public IPs on nodes
- Use internal load balancers for in-cluster services that need L4 exposure
- Restrict pod egress with network policies
- Use separate namespaces for ingress/system, web/API, workers, observability, and security tooling
- Default-deny outbound traffic from workloads
- Allow only private endpoints for PaaS and approved destinations through controlled egress policy

## 7. PaaS Connectivity and Security Constraint Compliance
### Azure Container Registry
- Public network access: Disabled
- Access only via Private Endpoint
- Image pull identity uses managed identity / workload identity with least privilege

### Azure Key Vault
- Public network access: Disabled
- Access only via Private Endpoint
- Used for TLS certs, application secrets, and encryption keys if applicable

### Azure Cache for Redis Premium
- Public network access: Disabled
- Access only via Private Endpoint
- Used for session cache, rate-limiting counters, hot read caching, and distributed locks if needed

### Azure Database for MySQL Flexible Server
- Public network access: Disabled
- Access only via Private Endpoint
- Use TLS, least-privilege DB users, and separate schema/user per service if microservices are used

## 8. PCI-DSS Security Design Considerations
### Encryption in transit
- TLS 1.2+ everywhere
- HTTPS from client to gateway
- Encrypted service-to-service traffic inside the cluster where possible
- Encrypted connections to MySQL and Redis

### Encryption at rest
- Ensure platform-managed encryption is enabled
- Use customer-managed keys only if required by policy and operationally feasible
- Protect backups and snapshots with the same standard

### Secrets management
- No secrets in container images or config maps
- Use Key Vault for all secrets and certificates
- Use workload identity / managed identity instead of static credentials where possible

### Logging and audit
- Log authentication events, authorization failures, admin actions, payment-related access, and secret access attempts
- Ensure logs do not contain PAN or sensitive authentication data
- Centralize immutable audit trails

### Access control
- Least privilege RBAC
- Separate duties for platform, app, and security operators
- Restrict production access with just-in-time and approval-based processes

## 9. Availability and Resilience Strategy
To target 99.99% uptime in a single region, design for failure at every layer:
- Use multiple node pools if needed for workload isolation
- Spread pods across availability zones if the region supports it and the platform design allows
- Use pod anti-affinity, topology spread constraints, PodDisruptionBudgets, and readiness/liveness probes
- Use a highly available Application Gateway configuration
- Use Redis Premium with high availability features appropriate to the chosen SKU
- Use MySQL Flexible Server HA configuration if available/required for the SLA
- Design application retry logic for transient failover events
- Keep the web tier stateless
- Use idempotent writes
- Use retry with exponential backoff
- Use graceful degradation if cache is unavailable
- Use queue buffering for non-critical work

## 10. Autoscaling Strategy
- Horizontal Pod Autoscaler for web/API/worker services
- Cluster autoscaling for node capacity
- Scale on CPU, memory, request rate, queue depth, and custom business metrics if needed
- Web/API services scale on request concurrency and CPU
- Workers scale on queue length and processing latency
- Read services scale on query latency and cache miss rate
- Keep a warm buffer to absorb spikes and node replacement events

## 11. Recommended Request Flow
### Synchronous user request
1. User sends HTTPS request to Application Gateway WAF v2
2. WAF inspects and forwards to AKS ingress
3. Ingress routes to Web/BFF service
4. Web/BFF calls internal business API service
5. Business API reads/writes MySQL via private endpoint, Redis via private endpoint, and Key Vault for secrets if needed
6. Response returns to user through gateway

### Asynchronous processing
1. Web/API service validates request
2. Writes transaction to MySQL
3. Publishes event or queue message
4. Worker consumes message
5. Worker performs background task
6. Worker updates DB/cache and emits audit event

## 12. Failure Handling and Operational Behavior
- If Redis is unavailable: continue with DB-backed fallback where possible and disable non-critical caching
- If MySQL is unavailable: fail fast for write operations and return controlled error responses
- If a worker fails: message is retried and poison messages go to dead-letter handling
- If ingress is under attack: WAF blocks malicious traffic, rate limits and custom rules reduce load, and the app remains protected behind the gateway

## 13. Key Design Decisions
- Public access only at Application Gateway WAF v2
- Private AKS cluster with no public node IPs
- All PaaS dependencies private-only
- Stateless web tier
- Queue-based background processing
- CQRS where read/write scaling differs
- Strict encryption and secret isolation for PCI-DSS
