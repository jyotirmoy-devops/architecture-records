# 1. Executive Summary

Design a highly secure, customer-facing web application on **Azure Kubernetes Service (AKS)** in **East US** with:
- **10,000 requests per minute** expected load
- **Auto-scaling** for both pods and nodes
- **99.99% uptime target** in a single region
- **PCI-DSS-aligned encryption and secret handling**
- **No public IPs on AKS nodes**
- **Ingress only through Application Gateway WAF v2**
- **All PaaS dependencies reachable only through Private Endpoints**
- Data/state services:
  - **Azure Cache for Redis (Premium)**
  - **Azure Database for MySQL Flexible Server**
  - **Azure Container Registry**
  - **Azure Key Vault**

This document combines the target architecture, security controls, data design, operational model, and FinOps baseline.

# 2. Architecture Overview

The solution uses a **private AKS-based application platform** with a single public ingress point:

1. Internet users connect to **Application Gateway WAF v2**.
2. Application Gateway forwards traffic to **AKS ingress**.
3. AKS hosts stateless web/API pods and async worker pods.
4. Application services access Redis, MySQL, Key Vault, and ACR only through **Private Endpoints**.
5. All PaaS public network access is disabled.
6. Azure Firewall controls outbound egress from AKS and platform subnets.

# 3. Target Azure Services

## 3.1 Public Edge
- **Application Gateway WAF v2**

  - WAF in Prevention mode
  - TLS 1.2+ only
  - Zone-redundant deployment where supported

## 3.2 Compute
- **Azure Kubernetes Service (AKS)**
  - Private cluster
  - Node pools with no public IPs
  - System and user node pools separated
  - Cluster Autoscaler enabled
  - Horizontal Pod Autoscaler enabled
  - Azure CNI Overlay or Azure CNI powered networking, depending on IP planning

## 3.3 Data / State

## 3.4 Security / Operations

- **Azure Monitor + Log Analytics**

# 4. Application Architecture

## 4.1 Recommended Application Pattern
Use a **modular microservices architecture** with a **Web-API + async worker** pattern:
- **Web tier**: stateless API services running in AKS
- **Async processing tier**: background workers for non-blocking tasks
- **CQRS-lite** where it helps:
  - Command side for writes/transactions
  - Query side for read-optimized endpoints using Redis caching
- **Event-driven integration** for internal decoupling
- **Transactional Outbox pattern** for reliable event publication

## 4.2 Proposed Service Boundaries
1. **Identity/Profile Service**
2. **Catalog/Content Service**
3. **Order/Transaction Service**
4. **Payment Orchestration Service**
5. **Notification Service**
6. **Audit/Compliance Service**
7. **Admin/Backoffice API**

## 4.3 Communication Patterns
- External/public APIs: **REST/JSON**
- Internal service calls: **REST/JSON** by default
- **gRPC** only for high-throughput low-latency internal paths
- **Async events/queues** for notifications, audit fan-out, reconciliation, and long-running workflows

# 5. Network Topology

## 5.1 Virtual Network Design
A single application VNet is acceptable if egress is controlled and subnet boundaries are enforced.

- **VNet Name:** `vnet-eastus-prod-app`
- **Region:** East US
- **Address Space:** `10.20.0.0/16`

### Subnets
1. **Application Gateway Subnet**
   - `10.20.0.0/24`
   - Dedicated subnet for App Gateway WAF v2
2. **AKS Node Subnet**
   - `10.20.1.0/22`
   - Private AKS node pools
3. **Private Endpoint Subnet**
   - `10.20.5.0/24`
   - Private Endpoints for ACR, Key Vault, Redis, MySQL
4. **Azure Firewall Subnet**
   - `10.20.6.0/26`
   - Dedicated for Azure Firewall
5. **Management / Jump Subnet**
   - `10.20.7.0/24`
   - Optional admin tooling

## 5.2 NSG / UDR Controls
- AKS subnet UDR routes default outbound traffic to Azure Firewall
- Deny direct internet egress from AKS nodes
- Allow only required outbound destinations
- Deny inbound to AKS subnet except from App Gateway subnet and required platform services

# 6. Private DNS Zones

Create and link the following Private DNS Zones to the application VNet:

- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

# 7. AKS Design

## 7.1 Cluster Configuration
- AKS private cluster
- No public IPs on nodes
- Managed identity for cluster operations
- Azure CNI networking
- Availability Zone spread across zones 1, 2, and 3 where supported
- Cluster Autoscaler enabled
- HPA enabled

## 7.2 Node Pools
### System Node Pool
- Runs core cluster components
- Minimum 3 nodes across zones
- Separate from application workloads

### User Node Pool
- Runs application pods
- Minimum 3 nodes across zones
- Autoscale enabled
- Taints/labels used to isolate workloads if needed

## 7.3 Ingress
- Use Application Gateway Ingress Controller (AGIC) or Application Gateway for Containers if approved
- Application Gateway WAF v2 is the only public ingress
- Enforce HTTPS only, TLS 1.2+, strong cipher suites, and WAF managed rules

## 7.4 Pod Security
- Non-root containers
- Read-only root filesystem where possible
- Dropped Linux capabilities
- Seccomp profiles
- Resource requests/limits
- Pod Disruption Budgets
- Topology spread constraints
- Anti-affinity for replicas

# 8. Security Architecture

## 8.1 Identity
- Microsoft Entra ID for human access
- MFA, Conditional Access, and Privileged Identity Management (PIM)
- Azure Workload Identity for pod-to-Azure authentication
- Avoid long-lived secrets in code or images

## 8.2 Private Endpoint-Only PaaS
All of the following must have public network access disabled:
- ACR
- Key Vault
- Redis
- MySQL Flexible Server

All access must be through Private Endpoints only.

## 8.3 Encryption
- TLS 1.2+ in transit everywhere
- Encryption at rest for all services
- Use Key Vault for secrets and certificates
- Prefer customer-managed keys where supported and operationally justified
- Rotate secrets and certificates on a defined schedule

## 8.4 Egress Control
- Route AKS outbound traffic through Azure Firewall
- Deny all outbound by default
- Allow only Azure service dependencies required for AKS operation, Private Endpoint destinations, and approved package repositories if needed
- Log all outbound flows
- Use FQDN filtering where appropriate

## 8.5 Supply Chain Security
- Store images in ACR Premium
- Enable image scanning via Defender for Cloud or integrated scanning
- Require signed images if your pipeline supports it
- Enforce admission controls for approved registries, namespaces, and pod security constraints
- Use CI/CD gates for SAST, dependency scanning, container scanning, and IaC scanning

# 9. Data Architecture

## 9.1 Azure Cache for Redis Premium
Use Redis for session state, caching, rate limiting, distributed locks, and short-lived tokens.
- Premium tier
- Private Endpoint only
- Public network access disabled
- TLS enforced
- Do not store system-of-record data

## 9.2 Azure Database for MySQL Flexible Server
Use MySQL as the transactional system of record.
- Private Endpoint only
- Public network access disabled
- TLS 1.2+
- Least-privilege DB users per service
- Automated backups enabled
- Point-in-time restore enabled
- HA enabled where supported and required for the SLA target

## 9.3 Azure Container Registry
- Premium SKU
- Private Endpoint only
- Public network access disabled
- Restrict pull permissions to AKS managed identity

## 9.4 Azure Key Vault
- Private Endpoint only
- Public network access disabled
- Store TLS certificates, application secrets, and encryption keys
- Enable soft delete and purge protection
- Use RBAC or access policies consistently
- Enable diagnostic logging

# 10. Availability and Resilience

## 10.1 Availability Target
The design targets **99.99% uptime in East US** using zone-aware App Gateway, zone-spread AKS node pools, multiple pod replicas, autoscaling, and HA-enabled data services where supported.

## 10.2 Resilience Controls
- Stateless application design
- Pod anti-affinity
- Topology spread constraints
- Pod Disruption Budgets
- Connection draining
- Retry with jitter
- Circuit breakers
- Idempotency keys for write operations
- Blue/green or canary deployments

## 10.3 Recovery Objectives
Recommended targets:
- **RTO:** 1 hour
- **RPO:** 15 minutes for transactional data, subject to MySQL backup/replication configuration

## 10.4 Backup and Restore
- MySQL automated backups with restore testing
- Key Vault soft delete and purge protection
- Infrastructure as Code for rebuild
- Periodic restore drills
- Documented rollback procedures for application releases

# 11. Observability and Operations

## 11.1 Logging
Centralize logs in Log Analytics and forward to SIEM/SOC:
- Application Gateway WAF logs
- AKS control plane logs
- AKS audit logs
- Container stdout/stderr
- Key Vault diagnostics
- ACR diagnostics
- Redis diagnostics
- MySQL diagnostics and slow query logs
- Azure Activity Logs
- Entra ID sign-in and audit logs
- Azure Firewall logs

## 11.2 Monitoring
Alert on WAF blocks and spikes, 5xx rates, latency degradation, pod restarts, HPA saturation, node pressure, DNS resolution failures, Private Endpoint health, Redis/MySQL availability, certificate expiry, and firewall deny spikes.

## 11.3 Operational Model
- Defined severity levels: Sev0 to Sev3
- On-call rotation for platform and application teams
- Change approval for production releases
- Rollback criteria for failed deployments
- Monthly restore test
- Quarterly incident simulation
- Patch cadence for base images and node pools

# 12. Compliance and Governance

## 12.1 PCI-DSS Alignment
- TLS 1.2+ enforced
- Encryption at rest enabled
- Secrets stored in Key Vault
- Least privilege access
- Network segmentation
- Centralized audit logging
- No public exposure of backend services
- Minimize cardholder data scope

## 12.2 Azure Policy
Use policy to deny public network access on ACR, Key Vault, Redis, and MySQL; public IPs on AKS nodes; noncompliant TLS settings; missing diagnostic settings; non-approved SKUs or regions; and unmanaged private endpoints.

## 12.3 Defender for Cloud
Enable container security recommendations, vulnerability assessment, posture management, threat detection, and the regulatory compliance dashboard.

# 13. Capacity and Scaling

## 13.1 Traffic Assumption
- 10,000 requests/minute = ~167 requests/second average
- Design for burst capacity above average load

## 13.2 Scaling Strategy
- HPA based on CPU, memory, and custom metrics
- Cluster Autoscaler for node growth
- Separate scaling profiles for web and worker workloads
- Pre-warm minimum replicas for customer-facing services

## 13.3 Suggested Baseline
- Minimum 3 AKS system nodes
- Minimum 3 AKS user nodes
- Application replicas: at least 3 across zones
- Redis and MySQL sized after load testing and query profiling

# 14. Data Protection and Backup Architecture

## 14.1 Azure Blob Storage
Azure Blob Storage is used for backups, exports, audit artifacts, and immutable retention where needed.
- Private Endpoint only
- Public network access disabled
- Use lifecycle policies for retention and tiering
- Enable soft delete and versioning where appropriate

## 14.2 Backup and Restore Controls
- Daily backup verification for MySQL
- Periodic restore drills into a non-production subscription
- Backup encryption with keys protected in Key Vault
- Access to backups limited to break-glass and platform operators
- Documented runbooks for MySQL point-in-time restore, Redis rehydration, Key Vault secret recovery, and AKS redeployment from IaC

# 17. Final Recommendation

Build the application as a **stateless, microservice-based, event-driven web platform** with:
- Application Gateway WAF v2 as the only public ingress
- AKS private cluster-style networking
- Private Endpoint-only access to ACR, Key Vault, Redis, and MySQL
- REST for external APIs and async events for backend workflows
- Transactional Outbox to ensure reliable event publication
- Redis caching to absorb read load and improve latency
- PCI-conscious data handling with minimal sensitive data exposure
