# 1. Executive Summary

Design a highly secure, customer-facing web application on **Azure Kubernetes Service (AKS)** in **East US** with:
- **10,000 requests per minute** expected load
- **Auto-scaling** for both pods and nodes
- **99.99% uptime target** in a single region
- **PCI-DSS-aligned encryption and secret handling**
- **No public IPs on AKS nodes**
- **Ingress only through Application Gateway WAF v2**
- **All PaaS dependencies reachable only through Private Endpoints**
- Data/state services:
  - **Azure Cache for Redis (Premium)**
  - **Azure Database for MySQL Flexible Server**
  - **Azure Container Registry**
  - **Azure Key Vault**

This document combines the target application, data, cloud, governance, and cost views into one technical architecture baseline.

# 2. Architecture Overview

The solution uses a **single-region hub-and-spoke Azure design** with:
- **Application Gateway WAF v2** as the only public ingress path
- **Private AKS cluster / private node networking** with no public IPs on nodes
- **Private Endpoint-only access** for ACR, Key Vault, Redis, and MySQL
- **Private DNS zones** for name resolution of all private services
- **Centralized logging and monitoring** for security and compliance evidence

## 2.1 Core design principles
1. **Zero Trust by default**
2. **Least privilege everywhere**
3. **Private-by-design**
4. **Defense in depth**
5. **Auditability**

# 3. Target Azure Services

## 3.1 Compute / Orchestration
- **Azure Kubernetes Service (AKS)**
  - Private cluster recommended
  - Node pools in **Availability Zones 1, 2, and 3** in East US
  - **Cluster Autoscaler** enabled
  - **Horizontal Pod Autoscaler (HPA)** enabled
  - **No public IPs on nodes**
  - Use **managed identity** for cluster operations

## 3.2 Ingress / Edge
- **Application Gateway WAF v2**
  - Public frontend IP for customer ingress
  - **WAF enabled in Prevention mode**
  - **Zone-redundant**
  - **Autoscaling enabled**
  - Integrated with AKS via **AGIC** or Application Gateway Ingress Controller pattern

## 3.3 Data / State
- **Azure Cache for Redis Premium**
  - Private Endpoint only
  - Public network access disabled
- **Azure Database for MySQL Flexible Server**
  - Private Endpoint only
  - Public network access disabled

## 3.4 Secrets / Images
- **Azure Key Vault**
  - Private Endpoint only
  - Public network access disabled
- **Azure Container Registry (ACR)**
  - Private Endpoint only
  - Public network access disabled

## 3.5 Supporting Security / Ops
- **Private DNS Zones**
- **Azure Monitor / Log Analytics**
- **Microsoft Defender for Cloud**
- **Azure Policy** for enforcement
- Optional: **Azure Bastion** for admin access to private resources

# 4. Application Architecture

## 4.1 Recommended application pattern
Use a **modular microservices architecture** with a **Web-API + async worker** pattern:
- **Web tier**: stateless API services running in AKS
- **Async processing tier**: background workers for non-blocking tasks
- **CQRS-lite** where it helps
- **Event-driven integration** for internal decoupling
- **No event sourcing** unless there is a strong audit/replay requirement

## 4.2 Proposed service boundaries
1. **Identity/Profile Service**
2. **Catalog/Content Service**
3. **Order/Transaction Service**
4. **Payment Orchestration Service**
5. **Notification Service**
6. **Audit/Compliance Service**
7. **Admin/Backoffice API**

## 4.3 Communication patterns
- **North-South traffic**: Client → Application Gateway WAF v2 → AKS Ingress
- **East-West traffic**: REST/HTTPS by default, gRPC only where needed
- **Async messaging**: queue/event-driven workers
- **Transactional Outbox pattern** for reliable event publication
- **Redis** for session state, hot read models, rate limiting, idempotency keys, and short-lived computed results

# 5. Network Topology

## 5.1 Recommended pattern: Hub-and-Spoke
Use a **hub VNet** for shared security services and a **spoke VNet** for the application.

### Hub VNet
Purpose: centralized security and admin access.
- **AzureFirewallSubnet**
- **AzureBastionSubnet**
- **Private DNS Resolver** or DNS forwarders

### Application Spoke VNet
Purpose: host AKS and private endpoints.

**Subnets**
1. **AppGatewaySubnet**
2. **AKS-Subnet**
3. **PrivateEndpoint-Subnet**
4. Optional **Management-Subnet**

## 5.2 Routing / Security
- **NSGs** on all subnets
- **UDRs** if using Azure Firewall for controlled egress
- **Deny-by-default** inbound posture
- AKS outbound should be tightly controlled to required Azure service dependencies only

# 6. Private DNS Zones Required

Create and link the following Private DNS Zones to the application VNet:
- `privatelink.azurecr.io`
- `privatelink.vaultcore.azure.net`
- `privatelink.redis.cache.windows.net`
- `privatelink.mysql.database.azure.com`

Ensure AKS can resolve these zones from the cluster nodes and pods.

# 7. Security Architecture

## 7.1 Mandatory controls
- **AKS nodes must not have public IPs**
- **Application Gateway WAF v2** is the only approved internet ingress path
- **All PaaS services must have public network access disabled**
- **Private Endpoints only** for ACR, Key Vault, Redis, and MySQL

## 7.2 Ingress security
- **Application Gateway WAF v2**
- WAF policy in **Prevention** mode
- Enable OWASP managed rules
- Enforce **HTTPS only**
- Use **TLS 1.2+**
- Prefer **end-to-end TLS** from App Gateway to AKS ingress

## 7.3 AKS security
- Use **private AKS cluster**
- Disable node public IPs
- Use **managed identities** for AKS and workload access
- Use **Secrets Store CSI Driver** with Key Vault integration for secrets

## 7.4 Identity and secrets
- Use **workload identity / managed identity** for AKS pods to access PaaS
- No secrets in code or container images
- Store certificates, connection strings, and keys in **Key Vault**
- Pods retrieve secrets at runtime through identity-based access

# 8. Data Architecture

## 8.1 Azure Cache for Redis Premium
**Purpose**
- Session state
- Response caching
- Distributed locks
- Short-lived tokens / throttling counters

**Configuration**
- **Premium tier**
- **Private Endpoint only**
- **Public network access disabled**
- TLS enforced in transit

**Usage guidance**
- Do not store PCI-sensitive primary data in Redis
- Store only transient or derived data
- Use short TTLs for session and cache entries

## 8.2 Azure Database for MySQL Flexible Server
**Purpose**
- System of record for transactional application data

**Configuration**
- **Private access only**
- **Public network access disabled**
- Zone-redundant deployment if available in region and supported for the chosen SKU
- Enforce TLS 1.2+ for all client connections
- Use least-privilege DB accounts per service

**Data model guidance**
- Separate schemas for customer profile data, order/transaction data, and audit/event metadata
- Avoid storing raw PCI data unless absolutely required; if card data is in scope, tokenize and minimize retention

## 8.3 Azure Blob Storage
**Purpose**
- Backup target for database exports and application artifacts
- Immutable audit archives if required
- Log retention and forensic snapshots

**Configuration**
- Private Endpoint only
- Public network access disabled
- Use lifecycle policies for retention and tiering
- Enable soft delete and versioning where appropriate

# 9. Availability, Replication, Backup, and DR

## 9.1 Availability target
- **SLA target: 99.99% in East US**
- Single-region design, but with zone-aware components where supported

## 9.2 Recommended high-availability posture
- **Application Gateway WAF v2** deployed zone-redundant if available
- **AKS node pools** spread across availability zones
- **MySQL Flexible Server** configured for zone redundancy if supported by selected SKU
- **Redis Premium** deployed with replication and failover capabilities appropriate to the chosen tier

## 9.3 Backup strategy
- **MySQL**: automated backups enabled, point-in-time restore retained per compliance and operational needs, regular restore testing
- **Redis**: if persistence is enabled, schedule backups/snapshots as supported; otherwise rely on application rehydration from MySQL
- **Key Vault**: soft delete + purge protection
- **Blob Storage**: versioning + soft delete; immutable retention for audit artifacts if required

## 9.4 RTO / RPO expectations
Recommended targets:
- **RTO:** 1 hour
- **RPO:** 15 minutes

# 10. Scaling Design

## 10.1 Traffic profile
- 10,000 requests/minute ≈ 167 requests/second average
- Design for burst capacity above average

## 10.2 Scaling approach
- **HPA** based on CPU, memory, and/or request rate/latency
- **Cluster Autoscaler** for node capacity
- Separate node pools logically by workload type if needed
- Consider **KEDA** for event-driven scaling if queue or background processing exists

## 10.3 Performance optimizations
- Cache read-heavy endpoints in Redis
- Use async processing for slow operations
- Keep request handlers short and deterministic
- Use pagination and filtering on all list endpoints

# 11. Logging, Monitoring, and Audit Policy

## 11.1 Mandatory log sources
- Application Gateway WAF logs
- AKS control plane logs
- AKS audit logs
- Container and application logs
- Key Vault diagnostic logs
- ACR audit/access logs
- Redis diagnostic logs
- MySQL audit/slow query/security logs where available
- Entra ID sign-in and audit logs
- Azure Activity Logs
- Network flow/security logs where applicable

## 11.2 Centralization
- Send all security-relevant logs to a centralized SIEM/SOC platform
- Retain logs according to PCI-DSS and internal policy
- Protect logs from tampering and restrict access to security/audit roles only

## 11.3 Alerting
Alert on:
- public network access changes
- Private Endpoint/DNS failures
- WAF blocks and anomalies
- privilege escalation
- secret access anomalies
- failed authentication spikes
- database access anomalies
- registry image pull anomalies

# 12. PCI-DSS Compliance Considerations

## 12.1 Key PCI-DSS-aligned controls
- Network segmentation and restricted access to cardholder data environment
- Strong encryption in transit and at rest
- Least privilege access
- Centralized logging and monitoring
- Vulnerability management and patching
- Secure configuration baselines
- Change control and approval workflow
- Regular access reviews

## 12.2 Important note
If the application processes cardholder data, the architecture must clearly define:
- whether AKS workloads are inside the CDE
- whether MySQL stores cardholder data or only tokenized data
- whether Redis contains sensitive session or token data

# 13. Governance Decisions Required

Before implementation, the architecture board should approve:
1. Whether the application is in PCI scope end-to-end or partially tokenized
2. Whether CMK is mandatory for all supported services
3. Whether break-glass access is allowed and how it is controlled
4. Whether outbound internet from AKS is fully blocked or allowlisted
5. Whether operational access is via bastion/jump controls or privileged remote access workflow
6. Whether the 99.99% target is a hard contractual SLA or an internal objective

# 14. Recommended Architecture Guardrails
- Enforce Azure Policy to deny:
  - public network access on approved PaaS services
  - public IP assignment to AKS nodes
  - noncompliant TLS settings
  - missing diagnostic settings
- Use policy-as-code in CI/CD for identity bindings, network rules, diagnostic settings, and private endpoint requirements
- Require security review for any change affecting ingress, identity, encryption, DNS, or private connectivity

# 15. Final Compliance Position
**Conditionally approved**, subject to the following mandatory controls:
- Private Endpoint-only access for ACR, Key Vault, Redis, and MySQL
- No public IPs on AKS nodes
- Application Gateway WAF v2 as the sole ingress path
- Entra ID + managed identity + workload identity
- Centralized logging and alerting
- TLS 1.2+ and encryption at rest
- Azure Policy enforcement for drift prevention
- Formal acceptance of single-region residual availability risk
