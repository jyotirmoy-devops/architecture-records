# Technical Architecture Document

## 1. Executive Summary
This document defines a highly secure, customer-facing Azure architecture for an AKS-based web application in **East US**. The design supports:
- **10,000 requests per minute** with autoscaling
- **99.99% uptime target** in a **single region**
- **PCI-DSS-aligned encryption and audit controls**
- **No public IPs on AKS nodes**
- **Application Gateway WAF v2** as the only internet-facing ingress
- **Private Endpoint-only access** for all PaaS services:
  - Azure Container Registry
  - Azure Key Vault
  - Azure Cache for Redis Premium
  - Azure Database for MySQL Flexible Server

The architecture is intentionally conservative and security-first. It uses private networking, managed identities, least privilege, centralized logging, and strict egress control.

## 2. Governance and Standards Check
A corporate wiki search was attempted, but the search endpoint returned an error and no internal standards could be retrieved.

**Result:** this design is based on Azure reference patterns and the requirements provided in the expert reports.

## 3. Important Design Decision: Single-Region Constraint vs. Availability Target
The original requirement asked for a single-region East US deployment with 99.99% uptime. The expert reports note that **99.99% end-to-end availability is difficult to guarantee in a single region**, even with zone-aware design and platform redundancy.

Per the expert guidance, the architecture remains **single-region East US**, but the availability target should be understood as a **best-effort high-availability objective** rather than a guaranteed SLA equivalent to a multi-region design.

**Why the original requirement was altered:**
- The expert reports explicitly state that a true 99.99% customer-facing SLA is not a good fit for a single-region-only design.
- To remain aligned with the expert reports, the design uses zone-aware and redundant patterns within East US, but does not claim multi-region resilience.

## 4. Target Architecture Overview
### Core components
- **Azure Application Gateway WAF v2**
  - Internet-facing entry point
  - WAF in prevention mode after tuning
  - TLS termination and optional re-encryption to AKS
- **Azure Kubernetes Service (AKS)**
  - Private cluster
  - No public IPs on nodes
  - System and user node pools
  - Autoscaling enabled
- **Azure Cache for Redis Premium**
  - Private Endpoint only
  - Used for caching, session state, and rate limiting
- **Azure Database for MySQL Flexible Server**
  - Private Endpoint only
  - System of record for transactional data
- **Azure Key Vault**
  - Private Endpoint only
  - Secrets, certificates, and key material
- **Azure Container Registry (ACR)**
  - Private Endpoint only
  - Container image storage and pulls
- **Azure Monitor / Log Analytics / AMPLS**
  - Centralized logging and monitoring with private connectivity where possible
- **Microsoft Defender for Cloud** and **Azure Policy**
  - Governance, posture management, and drift prevention

## 5. Network Topology
### Hub-spoke layout in East US
The design uses a single-region hub-spoke topology.

#### Hub VNet
Purpose: shared ingress, private endpoints, and network services.
- `snet-appgw` for Application Gateway WAF v2
- `snet-private-endpoints` for private endpoints to ACR, Key Vault, Redis, and MySQL
- `snet-bastion` optional, only if governed admin access is required
- `snet-azurefirewall` optional, only if centralized egress inspection is required

#### Spoke VNet
Purpose: AKS workload network.
- `snet-aks-system`
- `snet-aks-user`
- `snet-aks-pods` if needed for advanced pod networking
- `snet-aks-private-link` if needed for internal integrations

#### Connectivity
- Hub and spoke connected by **VNet peering**
- **NSGs** on all subnets
- **UDRs** for controlled egress if Azure Firewall is used
- **Private DNS zones** linked to both hub and spoke VNets

## 7. Security Architecture
### Mandatory controls
- Private AKS cluster
- No public IPs on AKS nodes
- Application Gateway WAF v2 as the only public ingress
- Private Endpoints only for ACR, Key Vault, Redis, and MySQL
- Public network access disabled on all PaaS services
- Managed Identity and Workload Identity for workload access
- TLS 1.2+ everywhere
- Defender for Cloud enabled
- Azure Policy deny assignments for public exposure drift
- MFA + PIM for administrators
- Least privilege RBAC
- No secrets in code or container images

### PCI-DSS alignment
- Encrypt data in transit and at rest
- Use Key Vault for secrets and certificates
- Mask PAN/CVV in logs
- Centralize audit logs
- Restrict access to cardholder data
- Rotate secrets and certificates regularly

## 8. AKS Design
### Cluster configuration
- Private AKS cluster
- Azure CNI Overlay or Azure CNI depending on IP planning
- System node pool and user node pool
- Cluster autoscaler enabled
- HPA enabled
- PDBs enabled
- Node pools spread across availability zones if supported in East US

### Suggested baseline
- 3 system nodes
- 3–6 user nodes
- VM size: `D4s_v5` or `D8s_v5` depending on workload profile

### Ingress
- Application Gateway Ingress Controller or AGIC-compatible pattern
- App Gateway terminates TLS
- Re-encrypt to AKS services if required by policy

## 9. Application and Service Communication Model
The application should use a **Web-Queue-Worker** pattern with **CQRS-lite** for read-heavy paths.

### Recommended service boundaries
1. **Web Frontend / BFF**
   - Serves browser traffic
   - Handles auth/session orchestration
   - Calls backend APIs
2. **Core Transaction API**
   - Customer-facing business operations
   - Writes to MySQL
   - Publishes async work items
3. **Read API**
   - Optimized for high-volume reads
   - Uses Redis cache aggressively
4. **Background Worker**
   - Processes emails, notifications, reconciliation, report generation, fraud checks, and other async tasks
5. **Admin/Operations API**
   - Optional
   - Restricted internal use only

### Communication rules
- **REST/HTTPS** for synchronous request/response
- **Service Bus queue/topic** for asynchronous work items and decoupling
- **Redis** for caching, rate-limited lookups, and short-lived state
- Use **timeouts, retries with backoff, circuit breakers, and correlation IDs**

## 10. Data and State Strategy
### Azure Database for MySQL Flexible Server
Use as the system of record for transactional data.
- Private Endpoint only
- Public access disabled
- TLS 1.2+
- Automated backups enabled
- Point-in-time restore configured
- Connection pooling from AKS

### Azure Cache for Redis Premium
Use for:
- Hot read caching
- Session/token lookup if needed
- Rate limiting counters
- Idempotency keys
- Short-lived computed results

Rules:
- Cache-aside pattern
- Short TTLs for sensitive data
- Explicit invalidation on writes where possible
- Never store raw PCI-sensitive data unless explicitly approved

### Azure Key Vault
Use for:
- TLS certificates for ingress
- Application secrets
- Database credentials if not using managed identity equivalents
- Key material and rotation

Rules:
- Public network access disabled
- Private Endpoint only
- Access via managed identities and least privilege

### Azure Container Registry
Use for:
- Container images for AKS deployments

Rules:
- Public network access disabled
- Private Endpoint only
- AKS pulls images over private connectivity only

## 11. Traffic Flow
1. Customer accesses the public application URL.
2. Traffic reaches **Application Gateway WAF v2**.
3. WAF inspects and forwards allowed traffic.
4. App Gateway routes to **AKS ingress/service**.
5. AKS application accesses:
   - Redis via Private Endpoint
   - MySQL via Private Endpoint
   - Key Vault via Private Endpoint
   - ACR via Private Endpoint for image pulls

## 12. Availability and Resilience
### Single-region resilience pattern
Because the design is constrained to East US only:
- Use availability zones where supported
- Use zone-redundant App Gateway if available
- Use multi-node AKS pools across zones
- Use MySQL HA if supported in the chosen deployment mode
- Use Redis Premium backup and restore strategy
- Use PDBs and rolling updates
- Use health probes and readiness/liveness probes

### Operational reality
A single-region design can be highly resilient, but it is **not equivalent to multi-region disaster recovery**.

## 13. Data Protection and Compliance
### PCI-DSS encryption
- TLS 1.2+ for all client/service communications
- Encryption in transit between client, App Gateway, AKS, Redis, MySQL, Key Vault, and ACR
- Encryption at rest using Azure-managed encryption by default
- Key Vault for secrets and certificates

### Public access prohibition
Per the requirement, the following must be disabled:
- ACR public network access: Disabled
- Key Vault public network access: Disabled
- Redis public network access: Disabled
- MySQL public network access: Disabled

All access must be via **Private Endpoints only**.

### Identity and access
- Managed Identities for AKS workloads where possible
- Least privilege RBAC
- Separate platform admin, app operator, and security operator roles
- Just-in-time access for administrative operations

## 14. Observability and Governance
### Logs to collect
- AKS control plane logs
- Container stdout/stderr
- App Gateway WAF logs
- Key Vault diagnostics
- ACR diagnostics
- Redis diagnostics
- MySQL diagnostics
- Azure Activity Logs
- NSG flow logs if enabled

### Governance controls
- Azure Policy to deny:
  - public IPs on AKS nodes
  - public network access on PaaS services
  - non-private endpoint deployments for approved services
  - non-HTTPS ingress
- Centralized logging and monitoring with private connectivity where possible
- Regular restore testing for MySQL backups
- Periodic failover and scale testing

## 16. Final Topology Summary
**Internet → Application Gateway WAF v2 → AKS private cluster → Private Endpoints → Redis / MySQL / Key Vault / ACR**

This design satisfies the stated security constraint by ensuring:
- AKS nodes have no public IPs
- All PaaS services are private-only
- PCI-DSS encryption is enforced
- The application can autoscale to meet 10,000 requests/minute
- The architecture remains single-region in East US with a high-availability objective
