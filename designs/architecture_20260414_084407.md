# Technical Architecture Document

## 1. Executive Summary
Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US, built for 10,000 requests per minute with autoscaling, 99.99% availability, and PCI-DSS-aligned encryption controls.

The application uses:
- AKS for stateless web/API workloads
- Application Gateway WAF v2 as the only public ingress
- Azure Cache for Redis Premium for caching/session acceleration
- Azure Database for MySQL Flexible Server for transactional state
- Azure Container Registry (ACR) for images
- Azure Key Vault for secrets, certificates, and encryption material

All PaaS services must be private-only:
- Public network access disabled
- Access only through Private Endpoints / Private Link
- AKS nodes must have no public IPs

## 2. Business Requirements
- Customer-facing web application
- 10,000 requests per minute
- Auto-scaling required
- 99.99% uptime target
- Single region: East US
- PCI-DSS encryption standards apply
- No public IPs on AKS nodes
- Ingress only through Application Gateway WAF v2
- Private Endpoints only for ACR, Key Vault, Redis, and MySQL

## 3. Architecture Overview
### Core patterns
1. Web-API pattern
   - Browser traffic enters through Application Gateway WAF v2.
   - Web tier in AKS serves UI and/or API endpoints.
   - Stateless services scale horizontally.

2. N-tier logical separation
   - Presentation layer: web frontend
   - Application layer: API/services
   - Data layer: MySQL
   - Cache layer: Redis

3. Twelve-Factor / stateless container pattern
   - No session state on pods.
   - All runtime config injected via environment variables / mounted secrets.
   - Enables safe autoscaling and rolling updates.

4. Cache-aside pattern
   - Read-heavy data and session-like data should be cached in Redis.
   - Application checks Redis first, then MySQL on cache miss.

5. Blue/green or rolling deployment
   - Use progressive rollout for application updates.
   - Prefer readiness/liveness probes and canary-style traffic validation at the ingress layer if supported by your delivery pipeline.

6. Event-driven async processing: recommended for non-user-facing work
   - Use background workers for email notifications, payment reconciliation, audit log enrichment, and report generation.

## 4. Target Azure Services
### Edge / Ingress
- Azure Application Gateway WAF v2

### Compute

  - Private AKS cluster

  - No public IPs on nodes
  - Cluster autoscaler enabled

### Container Supply Chain

## 5. Network Topology
### Virtual Network
Create a dedicated VNet in East US.

Suggested address space:
- 10.20.0.0/16

### Subnets
1. snet-appgw
   - 10.20.0.0/24
   - Dedicated to Application Gateway WAF v2
   - Must be large enough for autoscaling

2. snet-aks-nodes
   - 10.20.1.0/22
   - AKS node subnet

3. snet-private-endpoints
   - 10.20.8.0/24
   - Private Endpoints for ACR, Key Vault, Redis, MySQL

4. snet-aks-pods
   - If using Azure CNI Overlay or advanced pod networking, allocate accordingly
   - If using standard Azure CNI, size based on pod density requirements

### Network Security
- NSGs on AKS and private endpoint subnets
- UDRs only if required for forced tunneling or inspection
- Deny all inbound by default
- Allow only:
  - Internet → App Gateway public frontend on 443
  - App Gateway → AKS backend service ports
  - AKS → Private Endpoints on required service ports

Link all zones to the AKS VNet.

## 7. AKS Design
### Cluster Type
- Private AKS cluster
- API server accessible only from within the VNet or approved admin network

### Node Pools
- System node pool
  - 3 nodes minimum
  - Zone-redundant across 3 zones if available in East US
  - VM size sized for system workloads

- User node pool
  - 3+ nodes minimum
  - Zone-redundant
  - Autoscaler enabled
  - Separate pool for application workloads

### Security Controls
- No public IPs on nodes
- Azure AD integration / RBAC
- Pod Security Admission
- Network Policies: Azure CNI + Network Policy or Calico
- Secrets Store CSI Driver with Key Vault
- Image pull only from private ACR
- Restrict egress to only required destinations

### Scaling
For 10,000 requests/minute:
- Enable Horizontal Pod Autoscaler
- Enable Cluster Autoscaler
- Consider KEDA if event-driven scaling is needed
- Use readiness/liveness probes and PDBs

## 8. Application Gateway WAF v2 Design
### Configuration
- Public frontend IP
- WAF policy attached
- TLS 1.2+
- HTTP to HTTPS redirect
- End-to-end TLS to AKS ingress if required
- Autoscaling enabled
- Zone redundant deployment

### Security
- WAF in Prevention mode
- OWASP managed rules
- Custom rules for geo/IP restrictions if needed
- Rate limiting
- Bot mitigation patterns
- Backend health probes to AKS ingress service

### AKS Integration
- Use AGIC or ingress integration pattern compatible with Application Gateway
- Backend should point to internal AKS ingress service

## 9. PaaS Private Endpoint Design
### Azure Container Registry
- Disable public network access
- Private Endpoint in snet-private-endpoints
- Private DNS zone: privatelink.azurecr.io

### Key Vault
- Disable public network access
- Private Endpoint in snet-private-endpoints
- Private DNS zone: privatelink.vaultcore.azure.net
- Use for TLS certs, app secrets, CSI driver

### Redis Premium
- Disable public network access
- Private Endpoint in snet-private-endpoints
- Private DNS zone: privatelink.redis.cache.windows.net

### MySQL Flexible Server
- Disable public network access
- Private Endpoint in snet-private-endpoints
- Private DNS zone: privatelink.mysql.database.azure.com

## 10. PCI-DSS Security Controls
### Encryption
- In transit: TLS 1.2+ from client to App Gateway, TLS from App Gateway to backend services where applicable, Private Link traffic remains on Microsoft backbone
- At rest: Azure-managed encryption by default; prefer customer-managed keys in Key Vault where supported and required by policy

### Identity and Access
- Managed identities for AKS workloads
- Least privilege RBAC
- Separate admin and app identities
- No shared secrets in code

### Logging / Audit
- Centralize WAF logs, AKS audit logs, container logs, Key Vault diagnostics, MySQL diagnostics, Redis diagnostics
- Retain logs per PCI policy

### Network Segmentation
- Separate subnets
- Private endpoints only
- No public access to data plane services

## 11. High Availability / Resilience
To maximize single-region resilience in East US:
- Zone-redundant Application Gateway WAF v2
- AKS node pools spread across zones
- Multiple replicas for app pods
- PodDisruptionBudgets
- Readiness/liveness probes
- Redis Premium with HA enabled
- MySQL Flexible Server with zone-redundant HA if supported for the chosen configuration
- Backups and restore testing

## 12. Data Architecture
### Transactional data
- Azure Database for MySQL Flexible Server
- Use for customer records, orders, payments metadata, and audit-relevant business transactions
- Recommended configuration:
  - Zone-redundant HA
  - Private access only
  - TLS 1.2+
  - Automated backups enabled
  - Point-in-time restore
  - Geo-redundant backup storage if available for the chosen configuration

### Session and ephemeral state
- Azure Cache for Redis Premium
- Use for session storage, shopping cart state, token/session throttling, and hot lookup caching
- Recommended configuration:
  - Private Endpoint only
  - Disable public network access
  - Persistence enabled only if required by app design
  - Prefer cache-aside pattern; do not treat Redis as system of record

### Secrets and certificates
- Azure Key Vault
- Use for TLS certs for App Gateway, DB credentials or managed identity references, app secrets and signing keys
- Recommended configuration:
  - Private Endpoint only
  - Soft delete + purge protection enabled
  - RBAC-based access control
  - Key rotation policies

### Container images
- Azure Container Registry
- Use for signed container images and deployment artifacts
- Recommended configuration:
  - Private Endpoint only
  - Content trust / image signing
  - Defender for Cloud image scanning

## 13. Availability, Replication, and Backup Strategy
### Availability model
Because the requirement is 99.99% in a single region, the design should use:
- Zone-redundant AKS node pools across at least 2–3 availability zones in East US
- Application Gateway WAF v2 deployed zone-redundant where supported
- MySQL Flexible Server zone-redundant HA
- Redis Premium with high availability configuration appropriate to the chosen tier/region support

### Replication
- MySQL: primary with synchronous HA replica if zone-redundant HA is enabled; optional read replica only if needed for reporting or read scaling
- Redis: use built-in replication/HA features of Premium tier; treat as non-authoritative state
- Blob Storage: use LRS/ZRS depending on backup and compliance needs; if backup durability is critical, use GRS/RA-GRS for backup vault or backup storage, even though the app remains single-region

### Backup strategy
- MySQL: automated backups enabled, point-in-time restore, retention aligned to compliance policy
- Redis: if persistence is required, enable persistence as supported by the chosen Premium configuration; otherwise, rely on cache rebuild from MySQL
- Key Vault: soft delete and purge protection; key rotation and recovery procedures
- AKS: backup cluster manifests, Helm charts, and persistent volume data if any; use Azure Backup or GitOps-based redeployability
- Blob Storage: soft delete, versioning, and immutability for backup artifacts where required

## 14. RTO / RPO Targets
Recommended targets:
- RTO: 30 minutes
- RPO: 5 minutes

If stricter recovery is required, reduce RTO via GitOps-based cluster rebuild, pre-provisioned infrastructure, automated failover runbooks, and warm standby deployment patterns within the same region.

## 15. Operational Guidance
### CI/CD
- Build container images in pipeline
- Run unit/integration/security tests
- Push to ACR
- Deploy via GitOps or pipeline-driven manifests/Helm
- Use environment promotion: dev → test → staging → prod

### Configuration management
- Use separate config per environment
- Store secrets in Key Vault
- Keep non-secret config in Kubernetes ConfigMaps or pipeline variables

### Observability
- Centralized logs, metrics, and traces
- Track request latency, error rate, pod restarts, cache hit ratio, DB connection saturation, WAF blocks
- Add distributed tracing for service-to-service calls

## 16. Key Design Decisions Summary
| Area | Decision |
|---|---|
| Public ingress | Application Gateway WAF v2 only |
| AKS exposure | No public node IPs; private cluster networking |
| PaaS access | Private Endpoints only; public access disabled |
| App pattern | Stateless web/API + cache-aside + background workers |
| Internal comms | REST/HTTPS; gRPC only if needed for performance |
| Async processing | Queue-based worker pattern recommended |
| Data store | MySQL Flexible Server as system of record |
| Cache | Redis Premium for hot data/session acceleration |
| Secrets | Key Vault with managed identity/workload identity |
| Compliance | TLS 1.2+, encryption at rest, least privilege, auditability |
| Scaling | HPA + cluster autoscaling + multi-replica + zone spread |

## Notes
- The architecture requirement for all PaaS services to be private-only is reflected in the Private Endpoint line item.

## 18. Final Assessment
This design is conditionally approvable and aligns with the stated security and compliance requirements, provided that:
- Private Endpoint-only access is enforced for ACR, Key Vault, Redis, and MySQL
- AKS nodes have no public IPs
- Managed identities and least privilege are used throughout
- Centralized immutable logging is enabled
- TLS 1.2+ and encryption at rest are enforced
- Network isolation and egress control are policy-driven
- PCI scope is minimized and formally validated
