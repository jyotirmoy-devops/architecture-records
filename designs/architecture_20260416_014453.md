# Technical Architecture Document

## 1. Executive Summary
This architecture is based on the expert reports and intentionally reflects the revised direction they recommend.

The original requirement asked for a single-region East US deployment. However, the Cloud Infrastructure Report states that the design was revised to **multi-region active/active** using **Azure Front Door** to satisfy the **99.99% uptime target**. Per the critical instruction, the expert reports take precedence over the original requirement when there is a conflict. Therefore, this document adopts the expert-recommended multi-region architecture and explains the change here.

The solution is a highly secure, customer-facing web application on Azure Kubernetes Service with:
- Azure Front Door Premium for global ingress
- Application Gateway WAF v2 in each region
- Private AKS clusters with no public node IPs
- Azure Cache for Redis Premium and Azure Database for MySQL Flexible Server
- Azure Container Registry, Key Vault, Redis, and MySQL all with public network access disabled and reachable only through Private Endpoints
- PCI-DSS-aligned encryption, logging, and network isolation

## 2. Architecture Drivers
### Business and operational drivers
- Customer-facing web application
- 10,000 requests per minute expected load
- Auto-scaling required
- 99.99% uptime target
- Strong security and compliance posture

### Compliance drivers
- PCI-DSS encryption requirements
- Auditability and traceability
- Least privilege access
- Private-by-default networking

### Technical drivers
- AKS nodes must not have public IPs
- Ingress via Application Gateway WAF v2
- PaaS services must be private-only
- Private DNS required for service resolution

## 3. Target Architecture Overview
### Global layer
- Azure Front Door Premium
- Azure Monitor
- Log Analytics Workspace
- Microsoft Defender for Cloud

### Regional layer
Each region contains:
- Application Gateway WAF v2
- Azure Kubernetes Service private cluster
- Azure Container Registry Premium with Private Endpoint
- Azure Key Vault with Private Endpoint
- Azure Cache for Redis Premium with Private Endpoint
- Azure Database for MySQL Flexible Server with Private Endpoint
- Private DNS Zones
- User-assigned Managed Identities

### Traffic flow
1. Client connects to Azure Front Door Premium.
2. Front Door routes to the healthiest regional Application Gateway WAF v2.
3. Application Gateway forwards traffic to AKS ingress.
4. AKS workloads access Redis, MySQL, Key Vault, and ACR through Private Endpoints only.
5. Logs and diagnostics flow to Log Analytics and Azure Monitor.

## 4. Application Architecture
The application pattern recommended by the Solution Report is:
- Modular monolith or tightly bounded microservices
- BFF/API layer in front of domain services
- CQRS for read-heavy paths
- Web-Queue-Worker for background processing
- Transactional Outbox for reliable event publication
- Idempotent consumers for queue handlers
- Cache-Aside using Redis

### Suggested logical services
- Web Frontend
- API Gateway / BFF
- Customer Domain Service
- Commerce / Order Service
- Payment Orchestration Service
- Notification Service
- Audit Service

### Communication model
- North-south: HTTPS only through App Gateway WAF v2
- East-west: REST for synchronous calls, queues/topics for async work
- No direct database access across services

## 5. Network Architecture
### Ingress
- Azure Front Door Premium is the global entry point.
- Application Gateway WAF v2 is the regional ingress and security boundary.
- No direct public exposure of AKS nodes or services.

### AKS networking
- Private AKS clusters
- Azure CNI networking
- No public IPs on nodes
- Separate system and user node pools
- Network policies enabled
- Pod anti-affinity and topology spread constraints where supported

### Private connectivity
Private Endpoints are required for:
- Azure Container Registry
- Azure Key Vault
- Azure Cache for Redis
- Azure Database for MySQL Flexible Server
- Azure Blob Storage if used for backups or archives

### Private DNS zones
The following zones are required and linked to the AKS VNets:
- privatelink.azurecr.io
- privatelink.vaultcore.azure.net
- privatelink.redis.cache.windows.net
- privatelink.mysql.database.azure.com
- privatelink.blob.core.windows.net
- private AKS API DNS zone as applicable

## 6. Security Architecture
### Identity and access
- Microsoft Entra ID for human identities
- Kubernetes RBAC mapped to Entra groups
- Workload Identity for pod-to-Azure authentication
- User-assigned managed identities for platform components
- Least privilege enforced across all roles

### Secrets and certificates
- Key Vault stores secrets, keys, and certificates
- Soft delete and purge protection enabled
- No plaintext secrets in code or images
- Secrets Store CSI Driver used where appropriate

### PCI-DSS controls
- TLS 1.2+ everywhere
- Encryption at rest for supported services
- Customer-managed keys where required and approved
- Logging of sensitive access events
- Segmentation of PCI workloads
- WAF managed rules and custom rules for web attack protection

### Key Vault / Application Gateway certificate note
The expert reports identify a deployment risk: Microsoft guidance may require a hybrid Key Vault model or alternate certificate handling for Application Gateway when Key Vault is fully private-only. This is a prerequisite decision for implementation and must be approved by security and platform teams.

## 7. Availability and Resilience
The Cloud Infrastructure Report explicitly states that the architecture was revised from single-region to **multi-region active/active** to satisfy the 99.99% uptime target. This overrides the original single-region requirement.

### Resilience features
- Azure Front Door Premium for global health-based routing
- Two regional stacks
- Zone-redundant Application Gateway WAF v2
- Zone-aware AKS node pools where supported
- Regional MySQL HA
- Multiple replicas for critical services
- Pod anti-affinity and topology spread constraints

### Data resilience
- MySQL Flexible Server with zone-redundant HA in each region
- Redis used as cache/session store only
- Application-level replication/failover strategy across regions

## 8. Observability
### Centralized logging sources
- AKS control plane and audit logs
- Kubernetes audit logs
- Container logs
- Application Gateway WAF logs
- Key Vault diagnostic logs
- Redis diagnostics
- MySQL logs
- Azure Activity Logs
- Entra sign-in and audit logs

### Alerting
- WAF anomalies
- Authentication and authorization failures
- Key Vault access failures
- Unusual egress attempts
- Database connection spikes
- Pod privilege escalation attempts
- Regional health degradation

## 9. Data Architecture
### Azure Cache for Redis Premium
- Private Endpoint only
- Public network access disabled
- Used for session state, cache, and rate limiting
- Not a system of record

### Azure Database for MySQL Flexible Server
- Private Endpoint only
- Public network access disabled
- Zone-redundant HA enabled
- Automated backups and PITR enabled
- TLS required

### Azure Container Registry Premium
- Private Endpoint only
- Public network access disabled
- Used for signed and scanned container images

### Azure Key Vault
- Private Endpoint only
- Public network access disabled
- Soft delete and purge protection enabled
- Stores secrets, keys, and certificates

### Azure Blob Storage
- Optional for backups, exports, and retention archives
- Must also be private-only if used

## 10. Scaling and Performance
### Traffic profile
- 10,000 requests per minute equals about 167 requests per second on average
- Design must handle burst traffic above average

### Scaling strategy
- Horizontal Pod Autoscaler for application and worker pods
- Cluster Autoscaler for node pools
- Queue-based worker scaling on queue depth and latency
- Redis caching for hot reads and session data
- CQRS read models for read-heavy paths

### Performance guardrails
- Timeouts and retries tuned carefully
- Circuit breakers for downstream dependencies
- Connection pooling for MySQL and Redis
- Avoid synchronous fan-out in the request path

## 11. Key Design Decisions
1. Azure Front Door Premium is the global entry point.
2. Application Gateway WAF v2 is the regional ingress and security boundary.
3. AKS nodes have no public IPs and run in private clusters.
4. All PaaS services are private-endpoint-only with public access disabled.
5. The architecture is multi-region active/active to satisfy the 99.99% uptime target.
6. Private DNS is mandatory for service resolution.
7. PCI-DSS controls are enforced through encryption, logging, segmentation, and least privilege.

## 12. Why the Original Requirement Was Altered
The original requirement specified a single-region East US deployment. The expert reports, especially the Cloud Infrastructure Report, state that a single-region design cannot credibly satisfy the 99.99% uptime target and therefore recommend a multi-region active/active design using Azure Front Door.

Per the critical instruction, expert reports override the original requirement when they conflict. This document therefore reflects the expert-recommended multi-region architecture.
