# 1. Executive Summary

Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US, built for 10,000 requests per minute, with auto-scaling, 99.99% availability, and PCI-DSS-aligned encryption controls.

The application will use:
- AKS for containerized application workloads
- Application Gateway WAF v2 as the only internet ingress
- Azure Cache for Redis (Premium) for caching/session acceleration
- Azure Database for MySQL Flexible Server for transactional persistence
- Azure Container Registry (ACR) for images
- Azure Key Vault for secrets, keys, and certificates

All PaaS services must have public network access disabled and be reachable only through Private Endpoints.

# 2. Target Architecture

## 2.1 Core design principles
- Zero-trust network posture
- Private-only access to all PaaS services
- No public IPs on AKS nodes
- WAF-protected ingress only
- Managed identity first
- Least privilege RBAC
- Centralized logging and monitoring
- Encryption in transit and at rest

## 2.2 Primary application pattern
A secure web + API + cache + database pattern:
- Web frontend for browser traffic
- Backend API for business logic
- Redis for cache/session acceleration
- MySQL for system of record

## 2.3 Logical request flow
1. Customer browser connects over HTTPS to Application Gateway WAF v2.
2. WAF inspects traffic and forwards to AKS ingress.
3. AKS routes to frontend/API pods.
4. API pods access Redis, MySQL, Key Vault, and ACR over private networking only.
5. Logs and metrics flow to Azure Monitor / Log Analytics.

# 3. Availability and Scale

## 3.1 Traffic assumptions
- Expected load: 10,000 requests/minute
- Average throughput: ~167 requests/second
- Design for burst above average

## 3.2 Availability target
To support 99.99% uptime in a single region (East US):
- Use Availability Zones where supported
- Deploy zone-redundant Application Gateway WAF v2
- Spread AKS node pools across zones
- Use MySQL Flexible Server high availability where supported
- Run multiple replicas for stateless services
- Use pod disruption budgets
- Use health probes and autoscaling

## 3.3 Scaling controls
- Horizontal Pod Autoscaler for application pods
- Cluster Autoscaler for node pools
- Separate scaling for frontend, API, and worker workloads
- Connection pooling for MySQL
- Cache-aside pattern for Redis

# 4. Network Architecture

## 4.1 Virtual network
Recommended VNet in East US:
- Address space: 10.20.0.0/16

Recommended subnets:
- snet-appgw: Application Gateway WAF v2
- snet-aks-system: AKS system node pool
- snet-aks-user: AKS application node pool(s)
- snet-private-endpoints: Private Endpoints for ACR, Key Vault, Redis, MySQL
- snet-management: Optional private admin tooling

## 4.2 Network security controls
- AKS nodes have no public IPs
- AKS is deployed as a private cluster
- Application Gateway WAF v2 is the only public entry point
- All PaaS services have public network access disabled
- Private Endpoints are the only connectivity path to PaaS
- NSGs restrict east-west traffic
- Egress from AKS should be controlled using Azure Firewall or NAT Gateway depending on enterprise policy

## 4.3 Private DNS zones
Create and link these Private DNS Zones to the VNet:
- privatelink.azurecr.io
- privatelink.vaultcore.azure.net
- privatelink.redis.cache.windows.net
- privatelink.mysql.database.azure.com

# 5. Compute Architecture

## 5.1 AKS design
- AKS private cluster
- No public API server exposure
- No public IPs on worker nodes
- Azure CNI Overlay or Azure CNI depending on IP planning
- Prefer Azure CNI Overlay if IP conservation is important

## 5.2 Node pools
Recommended minimum:
- System node pool: 3 nodes, zone spread
- User node pool: 3 nodes minimum, zone spread
- Cluster Autoscaler enabled

Suggested starting VM family:
- D-series or E-series depending on CPU/memory profile

## 5.3 Workload design
Deploy separate workloads for:
- Web frontend
- Customer API
- Background workers

Controls:
- Horizontal Pod Autoscaler
- Pod Disruption Budgets
- Readiness/liveness probes
- Requests/limits defined for all containers
- Non-root containers
- Read-only root filesystem where possible

## 5.4 Ingress
- Application Gateway Ingress Controller (AGIC) or equivalent ingress integration
- TLS termination at Application Gateway WAF v2
- Re-encrypt to backend if required by policy
- WAF policy in prevention mode

# 6. Data and State Architecture

## 6.1 Azure Cache for Redis Premium
Use Redis for:
- Session state
- Cache-aside pattern
- Rate-sensitive lookups
- Short-lived tokens or counters

Security:
- Public network access disabled
- Private Endpoint only
- TLS required
- Not treated as system of record

## 6.2 Azure Database for MySQL Flexible Server
Use MySQL for:
- Transactional persistence
- System of record
- PCI-relevant application data, if applicable

Security and HA:
- Public network access disabled
- Private Endpoint only
- TLS enforced
- Zone-redundant high availability
- Automated backups and point-in-time restore
- Encryption at rest enabled by default

## 6.3 Azure Key Vault
Use Key Vault for:
- Secrets
- Certificates
- Encryption keys

Security:
- Public network access disabled
- Private Endpoint only
- Soft delete and purge protection enabled
- Prefer Managed Identity / Workload Identity access

## 6.4 Azure Container Registry
Use ACR for:
- Container image storage
- Image distribution to AKS

Security:
- Premium SKU
- Public network access disabled
- Private Endpoint only
- Managed identity-based image pulls

# 7. Security Architecture

## 7.1 PCI-DSS alignment
Controls included:
- TLS 1.2+
- Encryption at rest
- Secrets in Key Vault
- Managed identities / Workload Identity
- Least privilege RBAC
- WAF protection
- Private-only PaaS access
- No public IPs on AKS nodes
- Centralized logging and auditability

## 7.2 Identity and access
- Human access via Microsoft Entra ID
- Workload access via Managed Identity / Workload Identity
- Separate roles for platform admins, security admins, developers, operators, and auditors
- Use PIM for privileged access where possible

## 7.3 Supply chain security
- Private ACR only
- Image scanning and signing recommended
- Admission controls to block noncompliant images
- Minimal base images
- Non-root execution
- CI/CD should promote immutable image tags or digests

## 7.4 Egress control
Preferred: Azure Firewall for centralized egress inspection
Alternative: NAT Gateway for stable outbound SNAT with NSG restrictions
Restrict outbound internet access to only approved destinations

# 8. Observability and Operations

## 8.1 Logging and monitoring
Centralize into Log Analytics and Azure Monitor:
- AKS control plane logs
- Kubernetes audit logs
- Container logs
- Application Gateway WAF logs
- Key Vault diagnostics
- ACR diagnostics
- Redis diagnostics
- MySQL diagnostics
- Entra ID sign-in/audit logs

## 8.2 Alerting
Alert on:
- 5xx spikes
- WAF block anomalies
- Pod restarts
- Node pressure
- HPA saturation
- MySQL connection saturation
- Redis memory pressure
- Certificate expiration
- Private Endpoint or DNS failures
- AKS API access failures

## 8.3 Operational model
Required operational practices:
- Infrastructure as Code using Bicep or Terraform
- CI/CD with gated approvals
- Blue/green or canary deployment strategy
- Rollback procedures
- Runbooks for AKS outage, MySQL failover, Redis degradation, DNS/private endpoint failure, and certificate rotation
- Regular restore testing and game days

# 9. Governance and Policy

## 9.1 Mandatory Azure Policy controls
Enforce:
- No public network access on ACR, Key Vault, Redis, MySQL
- Private Endpoint required
- AKS nodes without public IPs
- Approved SKUs only
- Diagnostic settings enabled

- Tagging and resource locks where appropriate

## 9.2 Compliance controls
- Encryption in transit and at rest
- Key rotation policy
- Access reviews
- Audit logging retention
- Segregation of duties
- Change control for production

# 12. Key Risks and Mitigations

## Risk: Private DNS misconfiguration
Mitigation: automate DNS zone creation and validation in IaC.

## Risk: MySQL becomes a bottleneck
Mitigation: query tuning, connection pooling, read optimization, and load testing.

## Risk: AKS egress exposure
Mitigation: Azure Firewall or NAT Gateway with strict NSGs and route tables.

## Risk: Incomplete HA for single-region SLA
Mitigation: zone-redundant App Gateway, multi-zone AKS, MySQL HA, multiple replicas.

## Risk: Operational access to private cluster
Mitigation: private admin path via VPN/ExpressRoute/Bastion and Entra ID controls.

# 13. Final Assessment

This architecture is suitable for a PCI-DSS-sensitive, customer-facing application with strong security boundaries and private-only PaaS access. The most important implementation constraints are:
- No public IPs on AKS nodes
- No public access on ACR, Key Vault, Redis, MySQL
- Private Endpoints + Private DNS everywhere
- Zone-redundant deployment in East US
- Automated backup and restore testing
- WAF-protected ingress only
