# Technical Architecture Document

## 1. Executive Summary
Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US, built for 10,000 requests per minute with auto-scaling, 99.99% uptime, and PCI-DSS-aligned encryption.

The solution uses:
- AKS for stateless web/API workloads
- Application Gateway WAF v2 as the only public ingress
- Azure Cache for Redis Premium for caching/session acceleration
- Azure Database for MySQL Flexible Server for transactional state
- Azure Container Registry (ACR) for images
- Azure Key Vault for secrets, certificates, and encryption material

All PaaS dependencies must be reachable only through Private Endpoints with public network access disabled.

## 2. Architecture Principles
1. Private-by-default
2. Least privilege everywhere
3. No public IPs on worker nodes
4. Centralized ingress through WAF
5. Private DNS for all PaaS resolution
6. Encryption in transit and at rest
7. Immutable, auditable infrastructure
8. Policy-as-code enforcement
9. Segregation of duties
10. Minimize PCI scope

## 3. Target Azure Services
### Edge / Ingress
- Azure Application Gateway WAF v2
  - Public frontend IP for customer access
  - WAF policy in Prevention mode
  - TLS termination and optional end-to-end TLS to AKS services

### Compute
- Azure Kubernetes Service (AKS)
  - Private AKS cluster
  - Azure CNI networking
  - System and user node pools with no public IPs
  - Cluster Autoscaler enabled
  - Horizontal Pod Autoscaler (HPA) for app pods
  - Optional KEDA if event-driven scaling is needed

### Container Supply Chain
- Azure Container Registry (ACR) Premium
  - Public network access disabled
  - Private Endpoint only
  - Used for image pulls by AKS

### Secrets / Certificates
- Azure Key Vault
  - Public network access disabled
  - Private Endpoint only
  - Store TLS certs, app secrets, and encryption keys

### Data / State
- Azure Cache for Redis Premium
  - Public network access disabled
  - Private Endpoint only
  - Used for session/state caching

- Azure Database for MySQL Flexible Server
  - Private access only
  - Public network access disabled
  - Private Endpoint only
  - Use zone-redundant HA if available in the region and service tier

### Observability
- Log Analytics Workspace
- Azure Monitor / Container Insights
- Application Gateway diagnostics
- AKS control plane and workload logs

## 4. Network Topology
### Virtual Network
Deploy a dedicated VNet in East US with segmented subnets:
1. AppGatewaySubnet
   - Hosts Application Gateway WAF v2
   - Must be dedicated to App Gateway only
2. AKSSubnet
   - Hosts AKS node pools
   - No public IPs
   - NSG restricted to required east-west and ingress flows
3. PrivateEndpointSubnet
   - Hosts private endpoints for ACR, Key Vault, Redis, and MySQL Flexible Server
   - Disable private endpoint network policies on this subnet
4. Optional Management Subnet
   - For jumpbox or Azure Bastion if administrative access is required
   - Prefer Azure Bastion over public jump hosts

### Private DNS Zones
Create and link the following Private DNS Zones to the VNet:
- privatelink.azurecr.io
- privatelink.vaultcore.azure.net
- privatelink.redis.cache.windows.net
- privatelink.mysql.database.azure.com

If using a private AKS cluster, also include the AKS API server private DNS zone managed by AKS.

## 5. Security Architecture
### Internet Exposure
- Only Application Gateway WAF v2 is internet-facing.
- AKS, ACR, Key Vault, Redis, and MySQL are not publicly reachable.

### WAF Protection
- Enable OWASP Core Rule Set
- Add custom rules for:
  - Geo/IP restrictions if required
  - Bot mitigation
  - Header/query-string filtering
  - Rate limiting where appropriate

### AKS Hardening
- Use a private AKS cluster
- Disable public API server access
- Use managed identities for AKS and workloads
- Enforce:
  - Azure AD / Entra ID integration
  - Kubernetes RBAC
  - Pod Security Admission
  - Network Policies
  - Image signing/scanning if available in your pipeline

### PCI-DSS Encryption
- TLS 1.2+ for all external and internal traffic
- End-to-end encryption from client to App Gateway and from App Gateway to AKS services
- Use Key Vault for certificate and secret management
- Enable encryption at rest for MySQL, Redis, AKS disks, and logs/diagnostics where applicable

## 6. Application Architecture
### Core patterns
- Web + API on AKS
- CQRS-lite
- Cache-Aside
- Strangler-friendly modular monolith or service-oriented modularization
- Web-Queue-Worker for async work
- Idempotent command handling

### Suggested logical services
1. Web Frontend
2. API Gateway / BFF
3. Customer Core API
4. Transaction Service
5. Read Model Service
6. Async Worker Service
7. Admin Service

### Service communication model
- External traffic: HTTPS only through Application Gateway WAF v2
- Ingress to AKS: Application Gateway to Kubernetes ingress controller/service
- Internal synchronous calls: REST/HTTPS between services
- Async communication: queue-based worker pattern for background tasks
- Data access: application services connect directly to MySQL and Redis over private networking

## 7. Data Architecture
### Azure Cache for Redis Premium
Use for session state, hot data caching, rate limiting counters, and short-lived tokens or lookup data.
- Private Endpoint only
- Public access disabled
- TLS required

### Azure Database for MySQL Flexible Server
Use for system of record, transactional data, referential integrity, and audit-friendly relational storage.
- Private Endpoint only
- Public access disabled
- TLS required
- Encryption at rest enabled
- Backups and retention configured per compliance needs

### Data handling guidance
- Keep PCI-sensitive fields minimized
- Prefer tokenization or external payment processing if applicable
- Avoid storing raw cardholder data unless absolutely required by business scope

## 8. Availability and Scalability Design
### Availability target: 99.99% in a single region
To support this within East US:
- Deploy AKS across multiple availability zones if available for the region
- Run at least 3 replicas for critical stateless services
- Use PodDisruptionBudgets
- Use readiness/liveness probes
- Use horizontal pod autoscaling based on CPU, memory, and request metrics
- Use cluster autoscaling for node capacity growth
- Ensure Application Gateway is configured for high availability
- Use MySQL and Redis configurations that support zone-resilient or highly available deployment options where available

### Scaling approach
- Web/API pods: HPA based on RPS, CPU, and latency
- Worker pods: HPA based on queue depth and processing lag
- Redis: scale for cache throughput and memory pressure
- MySQL: scale vertically and tune connection pooling; use read patterns carefully

### Performance considerations
- Use connection pooling for MySQL
- Cache expensive reads in Redis
- Keep request handlers short and non-blocking
- Offload long-running tasks to workers

## 9. Ingress and Routing
- Application Gateway WAF v2 is the only public entry point
- Route by host/path:
  - / → web frontend
  - /api/* → API/BFF
  - /admin/* → admin service with stronger access controls

### Security controls at ingress
- WAF managed rules enabled
- Custom rules for IP reputation, geo restrictions if needed, request size limits, and bot mitigation patterns
- Enforce HTTPS redirect
- Use strong TLS policy
- Add rate limiting at app layer and/or gateway where feasible

## 10. Private Connectivity Model
All of the following must be private-only:
- ACR
- Key Vault
- Redis
- MySQL

### Required design elements
- Private Endpoints for each service
- Private DNS zones linked to the AKS VNet
- AKS pods resolve service FQDNs to private IPs
- Disable public network access on each PaaS resource
- Ensure CI/CD runners that push images or deploy secrets also have private network access to ACR/Key Vault if they interact directly

## 11. Governance and Policy Enforcement
Use Azure governance controls to prevent drift:
- Azure Policy to deny public network access on PaaS, public IPs on nodes, noncompliant SKUs, missing private endpoints, and missing diagnostic settings
- Resource locks for critical security resources
- IaC-only deployment with approval gates
- Periodic compliance review for PCI evidence

## 12. Logging and Monitoring
Collect and retain:
- AKS control plane audit logs
- Kubernetes API audit logs
- Container stdout/stderr
- Application Gateway WAF logs
- Azure Activity Logs
- Key Vault diagnostic logs
- ACR audit logs
- Redis diagnostics
- MySQL audit/slow query logs
- NSG flow logs if used
- Azure Policy compliance logs

Logs must be sent to a central SIEM / Log Analytics workspace, protected from tampering, and access must be read-only by default.

## 13. Required Encryption Policy
### In Transit
- TLS 1.2+ everywhere
- HTTPS only at ingress
- Encrypted connections from pods to Redis/MySQL/Key Vault/ACR
- Consider mTLS for service-to-service traffic inside the cluster if application complexity permits

### At Rest
- Enable encryption at rest for AKS persistent volumes, Redis, MySQL, Key Vault secrets, and logs/backups where supported

### Key Management
- Use customer-managed keys where supported and required by policy
- Store keys in Key Vault with public access disabled
- Enforce key rotation, access logging, and separation of key admins from app admins

### PCI-DSS Alignment
- Ensure cardholder data, if stored, is encrypted using strong cryptography
- Prefer tokenization and avoid storing PAN unless absolutely necessary
- Never log sensitive authentication data

## 14. Required Network Isolation Policy
### AKS
- AKS nodes must be deployed in a private cluster pattern or equivalent private control-plane access model
- Worker nodes must have no public IPs
- Restrict outbound access
- Use subnet-level segmentation
- Use Azure CNI or equivalent network model that supports enterprise segmentation and policy enforcement

### Ingress
- All inbound traffic must terminate at Application Gateway WAF v2
- No direct public exposure of AKS services
- Only required ports exposed
- WAF in prevention mode for production, with tuned exclusions

### Private Endpoints
All of the following must be private-only:
- ACR
- Key Vault
- Redis Premium
- MySQL Flexible Server

### DNS
- Private DNS zones must be used for all private endpoint name resolution
- DNS resolution must not fall back to public endpoints
- DNS changes must be controlled and audited

### Egress Control
- Restrict outbound internet access from AKS workloads
- Allow only approved destinations:
  - Azure PaaS private endpoints
  - required OS/package repositories via controlled egress path
  - monitoring endpoints if needed
- Block arbitrary outbound traffic

## 15. Service-by-Service Control Requirements
### Azure Container Registry (ACR)
- Public network access: Disabled
- Private Endpoint: Required
- Admin user: Disabled
- Pull access: via managed identity only
- Image scanning: required in CI/CD
- Immutable tags recommended

### Azure Key Vault
- Public network access: Disabled
- Private Endpoint: Required
- Soft delete and purge protection: Enabled
- Access via managed identity only
- Key rotation policy: Required

### Azure Cache for Redis Premium
- Public network access: Disabled
- Private Endpoint: Required
- TLS required
- Access keys must be stored only in Key Vault if used at all
- Prefer managed identity patterns where supported by the application design

### Azure Database for MySQL Flexible Server
- Public network access: Disabled
- Private Endpoint: Required
- TLS required
- Strong password policy if password auth is used
- Prefer private-only connectivity from AKS
- Backups encrypted and access-controlled

## 16. Availability and Resilience Assessment
### 99.99% Single-Region Feasibility
This is possible only if:
- AKS is deployed with zone-aware design where supported
- Application Gateway WAF v2 is deployed in a resilient configuration
- Redis and MySQL are configured for high availability options available in-region
- application is stateless where possible
- autoscaling is tuned for traffic spikes

### Important Limitation
A single-region design cannot fully protect against a full regional outage or large-scale Azure service disruption in East US.

## 18. Final Architecture Decision
Proceed with a private-only, policy-enforced AKS platform in East US, but require:
1. formal PCI scope definition,
2. explicit acceptance of single-region availability risk,
3. Azure Policy guardrails before deployment,
4. security review of egress and DNS design,
5. operational runbooks for incident response and key rotation.
