# Technical Architecture Document

## 1. Executive Summary
This document defines the technical architecture for a new corporate blog and news portal. The solution is a simple, governed enterprise web application for marketing to publish articles, with a database to safely store article text, author profiles, and reader comments.

The architecture intentionally follows the expert reports rather than the original requirement where they differ. In particular, the reports require:
- Azure Application Gateway v2 with WAF as mandatory public ingress
- Private endpoints for all sensitive backend services
- A right-sized Azure App Service Plan instead of Isolated v2
- Single-region deployment
- Strong IAM, logging, encryption, and network isolation controls

The original requirement was therefore refined into a more secure and operationally complete enterprise design.

## 2. Scope and Objectives
### In scope
- Public website for article reading
- Marketing/editor publishing workflow
- Author profile management
- Reader comments with moderation
- Secure storage of content and metadata
- Centralized logging and monitoring
- Private connectivity to backend services

### Out of scope
- Multi-region active/active deployment
- Full microservices decomposition
- Event sourcing
- Public direct access to backend data services

## 3. Architecture Principles
- Keep the solution simple and maintainable
- Use a modular monolith with background workers
- Expose only one public ingress point
- Keep all sensitive services private
- Enforce least privilege and MFA for non-public access
- Log all security and content lifecycle events
- Encrypt data in transit and at rest

## 4. Business and Governance Model
### Business ownership
- Marketing owns content creation and publishing
- Legal/compliance may review public statements and comment policy
- IT/security owns platform governance and controls

### Governance outcomes
- Public readers have read-only access to published content
- Marketing authors create drafts only
- Editors review and approve content
- Publishers have final publish rights
- Administrators manage infrastructure, not routine content editing

## 5. Application Architecture
### Recommended pattern
A **modular monolith with a Web-Queue-Worker pattern** is the best fit.

### Logical modules
#### 5.1 Content Publishing Module
Responsibilities:
- Create, edit, schedule, publish, unpublish articles
- Manage categories, tags, featured content
- Store article body, metadata, SEO fields, and publication status

#### 5.2 Author Profile Module
Responsibilities:
- Maintain author bios, photos, social links, and role information
- Associate authors with articles
- Support editorial staff profiles if needed

#### 5.3 Reader Comments Module
Responsibilities:
- Accept reader comments
- Store comment text, author name/email, moderation status, timestamps
- Support approve/reject/spam workflows

#### 5.4 Moderation & Workflow Module
Responsibilities:
- Review queued comments
- Handle article approval workflow if marketing wants draft review
- Trigger notifications for pending actions

#### 5.5 Public Read API / Website Delivery Module
Responsibilities:
- Serve published articles, author pages, category pages, and approved comments
- Optimize for read-heavy traffic
- Expose only published content to the public

### Communication style
- REST APIs for synchronous operations
- Queue-based asynchronous processing for moderation, notifications, indexing, and cache invalidation

### Event flow
1. Marketing editor creates or updates an article.
2. Application saves the draft in the database.
3. On publish, the system emits an `ArticlePublished` event.
4. Worker processes search indexing, cache refresh, and notifications.
5. Reader submits a comment.
6. Application stores the comment as `PendingModeration`.
7. System emits `CommentSubmitted`.
8. Worker runs spam checks and moderation routing.
9. Approved comments become visible on the public site.

## 6. Data Architecture
### 6.1 Primary relational store
**Azure SQL Database** is the system of record for:
- Articles
- Author profiles
- Comments
- Categories and tags
- Revisions
- Audit events

### 6.2 Media and rich content storage
**Azure Blob Storage** stores:
- Article images
- Downloadable assets
- Media attachments

### 6.3 Caching
**Azure Cache for Redis** is used for:
- Homepage and article list caching
- Author profile caching
- Comment count caching
- Session/state acceleration if needed

### 6.4 Optional future scale-out
**Azure Cosmos DB** is not required initially and should only be considered if comment scale or global distribution later justifies it.

### 6.5 Data model summary
#### Azure SQL Database tables
- `Articles`
- `Authors`
- `Comments`
- `ArticleTags` / `Categories`
- `AuditEvents`

#### Blob Storage containers
- `article-images`
- `author-profiles`
- `attachments`

### 6.6 Backup and recovery
- SQL automated backups with point-in-time restore
- Blob soft delete and versioning
- Redis treated as disposable cache
- RTO/RPO targets defined during implementation

## 7. Security Architecture
### 7.1 Identity and access management
Mandatory controls:
- Microsoft Entra ID SSO
- MFA for all admin and editorial users
- RBAC with least privilege
- Managed identity for service-to-service access
- No shared accounts

### 7.2 Ingress security
- Azure Application Gateway v2 with WAF is mandatory
- WAF runs in Prevention mode
- Managed rules enabled
- TLS 1.2+ enforced
- Rate limiting and bot protection enabled where appropriate

### 7.3 Data security
- SQL, Key Vault, Storage, and Redis use private endpoints
- Public network access disabled on all sensitive services
- Secrets stored only in Key Vault
- Encryption at rest enabled by default
- Diagnostic logs enabled for all resources

### 7.4 Logging and audit
Mandatory logs:
- Authentication events
- Failed login attempts
- Content creation, update, approval, publish, unpublish, delete
- Comment creation, moderation, deletion
- Permission changes
- Administrative configuration changes
- Database access events
- Security events and WAF alerts

### 7.5 Network isolation
- Public website tier separated from data tier
- Database not internet reachable
- Administrative interfaces isolated from public traffic
- Admin access only via corporate VPN, bastion, or approved secure access method

## 8. Azure Physical Architecture
### 8.1 Ingress and application flow
1. Public readers access the portal over HTTPS.
2. Traffic lands on Azure Application Gateway v2 with WAF.
3. Application Gateway forwards traffic privately to Azure App Service.
4. App Service uses regional VNet integration to reach backend services through private endpoints.
5. All sensitive data services are reachable only through private IPs.

### 8.2 Mandatory Azure services
- Azure Application Gateway v2 with WAF
- Azure App Service
- Azure App Service Plan
- Azure SQL Database
- Azure Storage Account (Blob Storage)
- Azure Key Vault
- Azure Cache for Redis
- Microsoft Entra ID
- Azure Monitor + Log Analytics

### 8.3 Network topology
#### Virtual network
- **VNet name:** `vnet-blog-prod`
- **Address space:** `10.40.0.0/24`

#### Subnets
1. `snet-appgw` — `10.40.0.0/27`
2. `snet-appsvc-integration` — `10.40.0.32/27`
3. `snet-private-endpoints` — `10.40.0.64/26`

#### Private DNS zones
- `privatelink.azurewebsites.net`
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`
- `privatelink.blob.core.windows.net`
- `privatelink.redis.cache.windows.net`

## 9. Availability and Resilience
Single-region deployment remains acceptable for this workload.

Recommended baseline:
- App Service with autoscale
- SQL automated backups and point-in-time restore
- Storage with zone-redundant option if region supports it
- Redis as cache only, not system of record
- Application Gateway health probes enabled

## 10. Operational Architecture
- Azure Monitor diagnostic settings on all resources
- Log Analytics workspace for centralized logs
- Alerts for WAF blocks, backend health, SQL connectivity failures, Key Vault access failures, Storage access failures, and Redis availability issues
- Backup and restore runbooks
- Content moderation workflow for comments

## 11. Data Classification and Handling
### Likely data types
- Public: published articles
- Internal/Confidential: drafts, editorial notes, unpublished content
- Personal data: author profiles, reader comments, IP logs

### Required handling
- Classify content by sensitivity
- Apply retention rules to comments and logs
- Minimize collection of personal data
- Define deletion and correction workflows for personal data requests
- Ensure moderation workflow for user-generated content

## 12. Application Security Requirements
Minimum controls:
- Input validation and output encoding
- Anti-CSRF protections for admin actions
- Secure session management
- Rate limiting and bot protection
- Content moderation workflow for comments
- Malware scanning for uploads, if any
- Dependency and vulnerability management
- Secure SDLC and code review for custom components

## 13. Key Decisions Required Before Build
1. Will comments be public, moderated, or disabled by default?
2. Will author profiles include personal contact details?
3. What is the retention period for comments and logs?
4. Who approves content before publication?
5. Will the portal integrate with corporate SSO?
6. Is the CMS managed, self-hosted, or custom-built?
7. What compliance obligations apply to reader data?

## 15. Architecture Risk Rating
**Overall Risk: Moderate**

Risk drivers:
- Public internet exposure
- User-generated content
- Administrative publishing privileges
- Potential personal data storage

Risk reduction depends on:
- Strong IAM
- Secure content moderation
- Proper network isolation
- Logging and monitoring
- Encryption and key management

## 16. Final Recommendation
Proceed with the portal only as a governed enterprise web application with:
- Strict role-based access
- Private database access
- Full audit logging
- Encryption everywhere required
- Segmented network design
- Moderated comments and privacy controls
