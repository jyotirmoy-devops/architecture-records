## 1. Executive Summary
Design a highly secure, customer-facing web application on Azure Kubernetes Service (AKS) in East US with:
- 10,000 requests per minute expected load
- auto-scaling required
- 99.99% uptime target in a single region
- PCI-DSS data encryption standards apply
- AKS nodes must not have public IPs
- ingress via Application Gateway WAF v2
- Azure Cache for Redis (Premium)
- Azure Database for MySQL (Flexible Server)
- all PaaS services (ACR, Key Vault, Redis, MySQL) must have public network access entirely disabled and be connected exclusively via Private Endpoints

This document consolidates the provided TOGAF, Cloud, Solution, Data, and FinOps reports into a single Technical Architecture Document.

## 2. Architecture Goals
- Secure customer-facing ingress through WAF-protected Application Gateway
- Private-only access to all PaaS dependencies
- Strong PCI-DSS-aligned encryption in transit and at rest
- Least-privilege identity and access management
- Centralized logging and monitoring
- Single-region high availability with zone-aware design where supported
- Scalable application tier for bursty traffic

## 3. Scope
### In Scope
- AKS application platform
- Application Gateway WAF v2 ingress
- Redis Premium
- MySQL Flexible Server

## 4. Target Architecture
### 4.1 Logical Flow
1. Internet users connect to Application Gateway WAF v2.
2. Application Gateway forwards traffic to the AKS ingress layer.
3. AKS workloads process requests and access:
   - Redis via Private Endpoint
   - MySQL via Private Endpoint
   - Key Vault via Private Endpoint
   - ACR via Private Endpoint for image pulls
4. Logs and diagnostics are sent to Azure Monitor / Log Analytics and the enterprise SIEM.

### 4.2 Core Components
- **Application Gateway WAF v2**: public entry point, WAF prevention mode, TLS termination and optional re-encryption.
- **AKS private cluster**: no public IPs on nodes, private API exposure, autoscaling enabled.
- **Azure Container Registry Premium**: public network access disabled, private endpoint only.
- **Azure Key Vault**: public network access disabled, private endpoint only, soft delete and purge protection enabled.
- **Azure Cache for Redis Premium**: public network access disabled, private endpoint only.
- **Azure Database for MySQL Flexible Server**: public network access disabled, private endpoint only.
- **Azure Monitor / Log Analytics**: centralized observability.
- **Azure Policy / Defender for Cloud**: compliance and guardrails.

## 5. Network Architecture
### 5.1 Connectivity Rules
- All customer traffic enters only through Application Gateway WAF v2.
- AKS nodes must not have public IPs.
- All PaaS services must be private-only.
- Private DNS resolution is mandatory for all private endpoint services.
- Egress from AKS must be restricted to approved destinations only.

### 5.2 Private Endpoint Matrix
| Service | Public Access | Private Endpoint | Private DNS Zone |
|---|---:|---:|---|
| ACR Premium | Disabled | Yes | `privatelink.azurecr.io` |
| Key Vault | Disabled | Yes | `privatelink.vaultcore.azure.net` |
| Redis Premium | Disabled | Yes | `privatelink.redis.cache.windows.net` |
| MySQL Flexible Server | Disabled | Yes | `privatelink.mysql.database.azure.com` |

### 5.3 DNS and Routing
- Use Azure Private DNS Zones linked to the AKS and Application Gateway VNet.
- If custom DNS is used, forward private zones appropriately.
- Treat DNS misconfiguration as a production outage risk.
- Use NSGs and UDRs to enforce segmentation and controlled egress.

## 6. Compute Architecture
### 6.1 AKS Design
- Private AKS cluster.
- System and user node pools with no public IPs.
- Cluster autoscaler enabled.
- Horizontal Pod Autoscaler enabled.
- Availability zone spread where supported.
- Network policies enabled.
- Managed identity / workload identity for Azure access.

### 6.2 Application Pattern
- Web + API + Worker pattern.
- Modular monolith or small service set.
- REST for synchronous flows.
- Queue/event-driven workers for asynchronous tasks.
- Stateless application pods.
- Redis for cache/session acceleration.
- MySQL for durable transactional state.

### 6.3 Resilience Patterns
- Readiness and liveness probes.
- Pod Disruption Budgets.
- Retry with exponential backoff.
- Circuit breakers.
- Timeouts on outbound calls.
- Graceful degradation for non-critical paths.

## 7. Data Architecture
### 7.1 MySQL Flexible Server
- Primary transactional datastore.
- East US deployment.
- Public network access disabled.
- Private Endpoint only.
- Zone-redundant HA if supported by SKU/region.
- Automated backups enabled.
- TLS 1.2+ enforced.
- CMK recommended where required by policy.

### 7.2 Redis Premium
- Session cache, distributed cache, throttling counters, hot data cache.
- Public network access disabled.
- Private Endpoint only.
- TLS in transit.
- Treat as non-system-of-record.

### 7.3 Key Vault
- Stores TLS certificates, secrets, and encryption keys.
- Public network access disabled.
- Private Endpoint only.
- Soft delete and purge protection enabled.
- Least-privilege access via managed identity.

### 7.4 ACR
- Private image registry for AKS workloads.
- Public network access disabled.
- Private Endpoint only.
- Admin user disabled.
- AKS pull access via managed identity.

## 8. Security Architecture
### 8.1 Identity and Access
- Microsoft Entra ID for human access.
- Managed identities for workloads.
- Azure RBAC for authorization.
- PIM for privileged roles.
- Break-glass accounts with monitoring and compensating controls.

### 8.2 Encryption
- TLS 1.2+ everywhere.
- Re-encrypt traffic from ingress to backend services where applicable.
- Encryption at rest enabled for all services.
- CMK preferred where supported and operationally feasible.
- No secrets in code, images, or manifests.

### 8.3 Logging and Monitoring
Mandatory log sources:
- AKS control plane and audit logs
- Kubernetes audit logs
- Application Gateway WAF logs
- Key Vault diagnostic logs
- ACR diagnostic logs
- Redis diagnostics
- MySQL diagnostics
- Azure Activity Log
- Entra ID sign-in and audit logs
- NSG flow logs if used
- Container runtime and workload logs

Alert on:
- WAF blocks and anomalies
- failed authentication spikes
- privilege escalation
- Key Vault access failures
- ACR unauthorized pulls
- MySQL connection anomalies
- Redis connection anomalies
- AKS API server access anomalies
- public network access re-enabled on any PaaS resource
- private endpoint or DNS resolution failures

## 9. Availability and Scaling
### 9.1 Availability Strategy
To support 99.99% uptime in a single region:
- zone-aware deployment where supported
- autoscaling for pods and nodes
- health probes and readiness/liveness checks
- monitored dependency health
- tested backup/restore and recovery procedures
- redundant ingress capacity

### 9.2 Scaling Strategy
Traffic assumption: 10,000 requests/minute, approximately 167 requests/second average with burstiness.

Scale controls:
- AKS HPA based on CPU, memory, and custom metrics
- Cluster Autoscaler for node pool growth
- Application Gateway autoscaling enabled
- Redis Premium sized for peak cache throughput
- MySQL Flexible Server sized for peak connection and IOPS demand

## 10. Governance and Policy Guardrails
Mandatory Azure Policy controls:
- Deny public network access on Key Vault, ACR, Redis, and MySQL Flexible Server
- Deny creation of AKS node pools with public IPs
- Require diagnostic settings on all critical resources
- Require private endpoints for approved PaaS services
- Require WAF on Application Gateway
- Require TLS minimum version enforcement
- Require managed identity where supported
- Require tagging for ownership, data classification, and environment
- Deny noncompliant regions and SKUs

## 11. Compliance Assessment
### PCI-DSS Alignment
This design can align with PCI-DSS if the following are enforced:
- network segmentation
- least privilege
- strong encryption
- logging and monitoring
- secure configuration management
- vulnerability management
- restricted access to cardholder data environment components

### Key Compliance Gaps to Watch
- Any public endpoint on PaaS services
- Weak secret management
- Incomplete logging retention
- Overly broad IAM roles
- Uncontrolled egress from AKS
- Missing private DNS validation

## 12. Operational Considerations
- Validate private DNS resolution early and continuously.
- Test restore procedures for MySQL regularly.
- Tune WAF policy to reduce false positives.
- Use image scanning and signed images where possible.
- Keep application pods stateless.
- Use connection pooling to protect MySQL.
- Store session state in Redis only if the application can tolerate cache failover.

## 15. Conclusion
The proposed architecture is a secure, private-by-default Azure design that satisfies the stated requirements:
- customer-facing ingress through Application Gateway WAF v2
- AKS nodes without public IPs
- private-only PaaS connectivity
- PCI-DSS-aligned encryption and logging
- autoscaling for the expected traffic profile
- single-region high availability posture in East US

The primary implementation risks are private DNS misconfiguration, policy drift, and insufficient operational testing. These should be controlled through policy-as-code, automated validation, and regular recovery exercises.
