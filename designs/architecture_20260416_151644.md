# Technical Architecture Document for Corporate Blog and News Portal

## 1. Purpose
This document defines the target architecture for a simple corporate blog and news portal where the marketing team can publish articles and a database safely stores article text, author profiles, and reader comments.

## 2. Scope
The solution includes:
- Public website for readers
- Authoring and moderation portal for marketing staff
- Backend application API
- Relational database for content and comments
- Media storage for images and assets
- Centralized logging and monitoring
- Edge security and WAF

## 3. Architecture Summary
The recommended solution is a simple, secure, single-region Azure web application with:
- Azure Front Door Premium as the public ingress and WAF layer
- Azure App Service Standard S1 for the website and authoring portal
- Azure SQL Database General Purpose, 2 vCores for articles, authors, and comments
- Azure Key Vault Standard for secrets
- Azure Storage Account GPv2, Hot, LRS for media assets
- Application Insights and Log Analytics for observability

This design intentionally follows the expert reports rather than the original requirement alone. The original requirement asked for a simple website and database, but the expert reports added necessary enterprise controls such as WAF, private connectivity, centralized logging, and managed identity. Those additions were adopted because they reduce security risk for an internet-facing corporate portal.

## 4. Logical Architecture
### 4.1 User-facing capabilities
- Public readers browse articles and approved comments
- Marketing authors create and edit drafts
- Marketing publishers approve and publish content
- Moderators review and remove comments

### 4.2 Application pattern
The application follows a modular web application pattern:
- Web frontend for public and authoring experiences
- Backend API for content operations
- Relational database for persistent content
- Optional background processing for moderation and notifications

### 4.3 Communication style
- REST APIs for web and admin operations
- Asynchronous queue-based processing for spam checks, notifications, and other background tasks if needed

## 5. Physical Architecture
### 5.1 Azure services and SKUs
| Layer | Azure Service | SKU / Tier | Purpose |
|---|---|---:|---|
| Edge / WAF | Azure Front Door | Premium | Public entry point, TLS termination, WAF, origin protection |
| Web App | Azure App Service Plan | Standard S1 | Hosts the blog/news portal and admin UI |
| Web App | Azure App Service | Windows or Linux Web App on S1 | Public website + marketing authoring portal |
| Database | Azure SQL Database | General Purpose, 2 vCores | Articles, author profiles, comments, moderation metadata |
| Secrets | Azure Key Vault | Standard | Connection strings, app secrets, certificates |
| Media | Azure Storage Account | General Purpose v2, Hot, LRS | Images, banners, attachments |
| Monitoring | Application Insights | Workspace-based | App telemetry, request tracing, dependency monitoring |
| Logging | Log Analytics Workspace | Pay-as-you-go | Central log retention and query |
| Optional cache | Azure Cache for Redis | Basic C0 | Read caching for published content |

### 5.2 Ingress and web tier
- Users access the site through Azure Front Door Premium
- Front Door provides WAF, HTTPS-only access, origin shielding, and optional bot/rate-limit rules
- Front Door forwards traffic to the App Service origin using Private Link where supported

### 5.3 Application tier
- Azure App Service Standard S1 hosts the web application
- Enable Managed Identity, Always On, HTTPS Only, and a staging slot
- App Service uses Regional VNet Integration for outbound private access to SQL and Key Vault

### 5.4 Data tier
- Azure SQL Database General Purpose, 2 vCores stores articles, author profiles, comments, categories, tags, and moderation/publishing audit data
- Configure Private Endpoint and disable public network access
- Enforce TLS 1.2+

### 5.5 Secrets and media
- Azure Key Vault Standard stores app secrets, certificates, and operational configuration secrets
- Azure Storage Account GPv2 Hot LRS stores article images, author avatars, hero banners, and exports/backups

## 6. Network Topology
### 6.1 Virtual network
- VNet name: `vnet-corp-blog-prod`
- Address space: `10.20.0.0/16`

### 6.2 Subnets
1. `snet-appsvc-integration` — `10.20.1.0/26`
   - Delegation: `Microsoft.Web/serverFarms`
   - Purpose: outbound private connectivity from App Service to SQL and Key Vault

2. `snet-private-endpoints` — `10.20.2.0/24`
   - Purpose: private endpoints for SQL, Key Vault, and optional App Service private endpoint/origin connectivity

3. `snet-admin` — `10.20.3.0/24`
   - Purpose: jumpbox or admin tooling if corporate policy requires controlled admin access

### 6.3 Private DNS zones
Link these zones to the VNet:
- `privatelink.database.windows.net`
- `privatelink.vaultcore.azure.net`
- `privatelink.azurewebsites.net`
- `privatelink.blob.core.windows.net` if Storage private endpoints are added later

## 7. Security Architecture
### 7.1 Public access model
- Only Azure Front Door is public
- The App Service origin should not be directly exposed to the internet
- SQL is not internet reachable
- Key Vault should be reachable only through private connectivity

### 7.2 Identity and access
- Use Microsoft Entra ID for staff authentication
- Enforce MFA for marketing and admin users
- Use role-based access control
- No shared accounts
- Use Managed Identity for app-to-SQL and app-to-Key Vault access
- Separate content authoring from platform administration

### 7.3 Encryption
- TLS 1.2+ end to end
- HTTPS only
- Encryption at rest enabled by default for SQL, Storage, and Key Vault
- Use customer-managed keys only if corporate policy requires them

### 7.4 WAF and edge protection
Use Azure Front Door Premium WAF with:
- Microsoft managed rule set
- rate limiting
- bot protection
- optional geo-filtering
- HTTPS redirect

## 8. Data and Storage Design
### 8.1 Azure SQL schema
Core tables:
- `Articles`
- `Authors`
- `Comments`
- `Categories`
- `Tags`
- `ArticleTags`
- `PublishingAudit`
- `ModerationStatus`

### 8.2 Blob storage containers
- `article-images`
- `author-avatars`
- `site-assets`
- `exports`

### 8.3 Cache
If read traffic grows, add Azure Cache for Redis Basic C0 for:
- published article pages
- author profile lookups
- navigation data
- comment counts

Redis remains non-authoritative.

## 9. Availability, Backup, and Recovery
### 9.1 App Service
- Use a staging slot for deployment validation
- Enable health checks
- Use Front Door health probes

### 9.2 SQL Database
- Automated backups
- Point-in-time restore
- Geo-restore available
- Consider failover group later if business continuity requirements increase

### 9.3 Storage
- Enable soft delete, versioning, and container soft delete
- Consider GZRS later if resilience requirements increase

### 9.4 Target recovery objectives
- RPO: 15 minutes or better
- RTO: 1 hour or better

## 10. Operational Model
### 10.1 Deployment pattern
1. Deploy VNet and subnets
2. Deploy SQL Database and private endpoint
3. Deploy Key Vault and private endpoint
4. Deploy Storage Account
5. Deploy App Service Plan Standard S1
6. Deploy Web App with Managed Identity
7. Configure VNet Integration
8. Configure Front Door Premium with WAF and Private Link origin
9. Link Private DNS zones
10. Disable public access where applicable

### 10.2 Logging and monitoring
Send logs to Log Analytics and SIEM:
- authentication events
- authorization failures
- publish/edit/delete actions
- comment moderation actions
- database access failures
- WAF events
- secret access events
- admin configuration changes

## 11. Compliance and Governance
Relevant control families include:
- NIST AC: access control
- NIST AU: audit and accountability
- NIST SC: system and communications protection
- NIST IA: identification and authentication
- CIS Controls: least privilege, secure configuration, logging, data protection

If the portal collects personal data from commenters or authors, privacy obligations may apply, including privacy notice, consent or legitimate interest basis, retention and deletion policy, and data subject request handling.

## 12. Decision and Rationale
The original requirement was altered to include enterprise security controls because the expert reports identified the portal as a public-facing application with moderate-to-high security exposure. The final design therefore includes WAF, private connectivity, centralized logging, managed identity, and explicit Azure service selections.
